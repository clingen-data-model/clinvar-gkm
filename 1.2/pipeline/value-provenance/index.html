Where a Value Comes From¶

What this page answers

Where a value in a published bundle came from: the ClinVar data it was read from, and the pipeline step that built it. Read it when you need to know whether a field is ClinVar's own value, a lookup, or something the pipeline computed, or to find the procedure page that explains it in full.

Every value in a bundle starts in ClinVar's XML release. The upstream clinvar-ingest pipeline loads the XML into relational BigQuery tables (variation, scv_summary, clinical_assertion, trait, rcv_mapping and others); the procedures in src/procedures/ read those tables and build one gkm_dict_* table per bundle section; the assembler turns those tables into the bundle (Export & Distribute).

How to Read the Tables¶

Each table below has four columns:

  • Field — the bundle section and property, as on the Output Format pages
  • ClinVar source — the ingested table and column the procedure reads. Where it reads part of a record's content (the rest of the XML element, kept as JSON), the XML element is named, e.g. HGVSlist element. Lookup marks a value taken from a ClinVar-GKM mapping table rather than from the release, and Computed one the pipeline derives.
  • Built in — the pipeline page and step that document it, and the procedure file
  • Notes — what happens to the value on the way

The procedures and their files:

Procedure File Builds
variation_identity variation-identity-proc.sql The expression sent to vrs-python, HGVS, locations and cross-references per variation
gkm_catvar_proc gkm-catvar-proc.sql variation, allele, location, sequenceReference, copy number sections, gene
gkm_scv_condition_proc gkm-scv-condition-proc.sql condition, ClinVar trait sets in conditionSet, each SCV's resolved condition
gkm_scv_statement_proc gkm-scv-statement-proc.sql scv, SCV propositions, SCV evidence lines, therapy, therapyGroup, submitter
gkm_vcv_proc, gkm_vcv_statement_proc gkm-vcv-proc.sql, gkm-vcv-statement-proc.sql vcv, VCV propositions and evidence lines, condition sets minted for VCVs
gkm_rcv_proc, gkm_rcv_statement_proc gkm-rcv-proc.sql, gkm-rcv-statement-proc.sql rcv, RCV propositions and evidence lines

VRS Records¶

The allele, copyNumberCount, copyNumberChange, location and sequenceReference sections hold the VRS records a variation points to. Their identifiers are computed by vrs-python, not read from ClinVar.

Field ClinVar source Built in Notes
What vrs-python is given One expression per variation, the best-ranked of: the CanonicalSPDI element, an HGVS expression from HGVSlist, or a gnomAD-style expression from the VCF fields of the Location element Variation Identity, Precedence Hierarchy; VRS Processing SPDI ranks first. Transcript and protein expressions are not translated
allele id (ga4gh:VA.…), digest, state Computed by vrs-python VRS Processing; Cat-VRS, Step 2b A VRS identifier is a digest of the normalized allele, so the same allele always gets the same id
allele expressions (SPDI, hgvs.g, gnomad) The SPDI sent to vrs-python; HGVS from HGVSlist; gnomAD (chr-pos-ref-alt) from the VCF fields of the Location element; HGVS derived from Location coordinates Cat-VRS, Step 2, Step 2b Gathered from every variation that normalizes to the same allele. See HGVS and SPDI
allele name Computed: the top-ranked of the allele's expressions Cat-VRS, Step 2b
copyNumberCount, copyNumberChange records Computed by vrs-python from the copy number data above VRS Processing
location id (ga4gh:SL.…), start, end Computed by vrs-python Cat-VRS, Step 1b; VRS Processing, Step 3 Coordinate ranges for imprecise ends are rebuilt in the procedure
sequenceReference key (SQ.…), name, assembly extension Computed refget accession; the sequence accession and assembly version of the expression Cat-VRS, Step 1a; SequenceReference Extensions Assembly is written as GRCh38, GRCh37 or NCBI36

VCV and RCV Statements¶

The vcv and rcv sections are not copied from ClinVar's own VCV and RCV classifications: the pipeline recomputes each aggregate from the SCVs, following ClinVar's rules (Aggregation Rules). Field reference: VCV Statements, RCV Statements.

From Tables to the Bundle¶

The assembler (src/scripts/assemble-gkm-dicts.py with gkm_json_cleanup.py) changes the form of values, not their content. It drops null and empty fields, collapses typed extension values (value_<type>) to value, sorts the few arrays whose order carries no meaning, and writes each record as compact JSON with its keys sorted, so an unchanged record has the same bytes in every release (Export & Distribute, Step 2).

Tracing One Value¶

The proposition of clinvar.submission:SCV008145211.1 (the record in the annotated walk-through) has "object": "#/condition/clinvar.trait:66395". Its path back to ClinVar:

  1. The submitter named the condition with a MONDO code, MONDO:0800400, on the submitted trait (clinical_assertion_trait).
  2. gkm_scv_condition_proc matched that code to ClinVar trait 66395 through ClinVar's trait mapping; the SCV's submittedCondition extension records it as "normalized_resolution": "tm reftype xref mondo" and "condition": "clinvar.trait:66395" (Condition Mapping).
  3. The condition record clinvar.trait:66395 comes from the trait table: its name, RP1-related dominant retinopathy, and its MedGen primaryCoding, CN322606 (Traits).
  4. gkm_scv_statement_proc wrote the proposition's object as a pointer to that record (Step 5: Primary Proposition).
