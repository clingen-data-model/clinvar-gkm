Working in Python¶

ClinVar-GKM records are GA4GH objects, so the GA4GH Python reference implementations read them directly: vrs-python (ga4gh.vrs), cat-vrs-python (ga4gh.cat_vrs) and va-spec-python (ga4gh.va_spec), collected with other tools in the GKM Starter Kit. This page loads records from a bundle and from Parquet, follows their #/section/id pointers, builds the libraries' pydantic models from them, and serializes the models back to JSON.

It assumes the bundle layout described in Output Format and ID References, and, for the Parquet section, the tables described in The 20 Tables.

Tested with

Every code block on this page was run on 2026-11-21 with:

  • Python 3.14.5 (an earlier run, on 1.1.0 data, used 3.12.8), ga4gh.vrs 2.4.0a6, ga4gh.cat_vrs 0.8.0a6, ga4gh.va_spec 0.5.0a7, ga4gh.gkm 0.4.1, pydantic 2.14.4, duckdb 1.5.4, pyarrow 26.0.1, ijson 3.6.0, requests 2.34.2, gkm-bundle-parquet 2.0.0 (through uv 0.6.14), and the ClinVar-GKM schema tree at tag 1.2.0.
  • Bundle examples: 1.2.0 data, the 2026-11-15 weekly delta.
  • Parquet examples: the published 2.0 tables at v1/1.2/parquet/ (2026-11-15 release), and a mini-bundle cut from the 2026-11 full bundle.

The Parquet files are written with DuckDB 1.5.4: the duckdb_version in their manifest.json.

Prerequisites

  • Python 3.11 or later (the model libraries need 3.10, ga4gh.gkm 3.11), with the packages in Install.
  • git, to get the schema tree for Validate a bundle.
  • uv, for uvx gkm-bundle-parquet in Statements, propositions and variants, or pip install gkm-bundle-parquet==2.0.0 instead.
  • Network access to data.clinvar-gkm.org (the delta, and the Parquet tables, which the examples read remotely) and w3id.org (schemas fetched on demand).
  • Data: the 5 MB weekly delta from Get the example files. Only the gkm-bundle-parquet select example reads a full bundle: 4.9 GB compressed (68.5 GB decompressed), streamed from disk, about 10 minutes.

Run the Python blocks in order, in one Python session: each block uses the names (bundle, resolve, scv, vrs, rows, …) defined by the blocks before it.

Install¶

ClinVar-GKM 1.2.0, like 1.1.0, is written to VRS 2.1.1, Cat-VRS 1.1.1, VA-Spec 1.1.0 and GKM-Core 1.3.0, so the same library versions read both. The library releases that implement exactly those versions are, as of this writing, pre-releases:

Get the example files¶

The bundle examples use one small file, clinvar-gkm-delta_2026-1115.json.gz (5 MB): the published 2026-11-15 weekly delta, a 1.2.0 bundle of every record that changed that week.

Its path changes when its month ends (it moves to deltas/2026-11/), so the commands look it up in the line's index.json:

DELTA=$(curl -fsS https://data.clinvar-gkm.org/v1/1.2/index.json | python3 -c '
import json, sys
print(next(d["bundle"]["path"] for d in json.load(sys.stdin)["deltas"] if d["release"] == "2026-11-15"))')
curl -fsO "https://data.clinvar-gkm.org/${DELTA}"

The full bundles are about 4.9 GB compressed (68.5 GB decompressed). Don't json.load one; see Large bundles.

The repository also has nch-igm-bundle.json.gz (1.6 MB), a self-contained 1.1.0 sub-bundle of every SCV from one submitter, cut with Sub-Bundle Extraction, in which every pointer resolves inside the file (curl -fsLO https://github.com/clingen-data-model/clinvar-gkm/raw/4a47d6dc1ecfbc1d26364bacdbd2f8d258512f17/nch-igm-bundle.json.gz). The same libraries read it; validate it against the schema tree at tag 1.1.0, not 1.2.0.

Load a bundle and follow pointers¶

A bundle is one JSON object whose sections map an id to a record. json.load is enough to read one:

import gzip
import json

with gzip.open("clinvar-gkm-delta_2026-1115.json.gz", "rt") as f:
    bundle = json.load(f)

print(bundle["schema_version"])
print({section: len(records) for section, records in bundle.items() if isinstance(records, dict)})


def resolve(pointer):
    """Return the record that a '#/section/id' pointer names."""
    section, key = pointer.removeprefix("#/").split("/", 1)
    return bundle[section][key]

A delta is not self-contained

A weekly delta carries only the records that changed, so its pointers can name records that are only in the full bundle it applies to. The 2026-11-15 delta, for example, has no sequenceReference section, and 57 of its alleles and copy-number changes point to a location that is only in the full bundle. Resolve a delta's pointers against the full bundle after applying the delta.

Into the GA4GH models¶

Each section's records, except the ClinVar custom propositions, validate as one class from the libraries. A pointer string is accepted wherever a field allows a reference: the models type it as iriReference, and its .root holds the pointer.

VRS alleles and their identifiers¶

Continuing from the pointer walk above (allele, location, sequence):

from ga4gh.core import ga4gh_identify
from ga4gh.vrs import models as vrs

vrs_allele = vrs.Allele(**allele)
print(type(vrs_allele.location).__name__, vrs_allele.location.root)


def content(record):
    """A record without its stored identifiers."""
    return {k: v for k, v in record.items() if k not in ("id", "digest")}


# Recompute the VRS identifier from content alone: inline the location and its sequence reference
fresh = vrs.Allele(**content(allele) | {"location": content(location) | {"sequenceReference": sequence}})
print(ga4gh_identify(fresh), ga4gh_identify(fresh) == allele["id"])

iriReference #/location/ga4gh:SL.sF-Pr6l0-_uRAtk8bv9UzOPYvr6TK9IC
ga4gh:VA.1Oo5_TVyd33l8M9QsAac-ULaZR86hDCx True

ga4gh_identify needs the location inline: the allele's digest is computed over its location's digest, and the location's over its sequence reference, of which it uses only type and refgetAccession. Recomputed this way, every allele and copyNumberChange id in the delta whose location is also in the delta (176 of 233) matches the published id.

Records in the scv, vcv and rcv sections load as Statement, and evidenceLine records as EvidenceLine. The ClinVar-GKM statement profiles (ClinvarScvStatement, ClinvarVcvStatement, ClinvarRcvStatement) add no top-level fields to VA-Spec's Statement; their ClinVar-specific content is in extensions.

Extensions and ClinVar-specific types¶

  • Extensions load as GKM-Core Extension objects. name is a string; value keeps whatever JSON the record holds, including the structured values such as submittedCondition and clinvarHgvsList. The libraries don't interpret them. Statement extensions and Variations document each one.
  • ClinVar custom propositions have no class in va-spec-python yet. The propositionClinvarCustom section holds ClinVar's own germline proposition types (ClinvarOtherProposition, ClinvarRiskFactorProposition, …). Work with them as plain JSON, as the bundle provides them. Every other section loads into a library class without loss; see Round trip.

The GKM Toolkit¶

The GKM Toolkit (ga4gh.gkm) validates a producer's bundle against that producer's schemas. That is its intended way to validate producer data: you supply the schemas, and it checks every record against them. Validation works on ClinVar-GKM 1.2.0 and 1.1.0 bundles today; the toolkit's loader does not yet read them (see Loading bundles).

Validate a bundle¶

Call validate_bundle_schema with a validator= whose referencing registry holds the ClinVar-GKM 1.2.0 schemas and the GA4GH schemas they reference, taken from the schema/ tree of this repository at tag 1.2.0 (for a 1.1.0 bundle, use tag 1.1.0). The release checks use the same schemas; Release Validation lists the results, and its verification reports record, per published file, the schemas and tool versions used.

Get the schema tree. The GA4GH schemas come in through the va-spec submodule:

git -c advice.detachedHead=false clone -q --depth 1 --branch 1.2.0 --recurse-submodules --shallow-submodules \
    https://github.com/clingen-data-model/clinvar-gkm.git clinvar-gkm-1.2.0

Register every schema in the tree by its $id, then validate the delta (bundle, and scv from the pointer walk):

import os
from collections import Counter
from pathlib import Path

from jsonschema import Draft202012Validator
from referencing import Registry, Resource
from ga4gh.gkm.bundles import BundleValidationError
from ga4gh.gkm.bundles.schema_validation import validate_bundle_schema

# Every schema in the 1.2.0 tree, keyed by $id: ClinVar-GKM's own and the GA4GH schemas they reference
schemas = {}
for directory, _, files in os.walk("clinvar-gkm-1.2.0/schema", followlinks=True):
    for name in files:
        try:
            document = json.loads(Path(directory, name).read_text())
        except (ValueError, UnicodeDecodeError):
            continue  # Makefiles and YAML sources
        if isinstance(document, dict) and "$id" in document:
            schemas[document["$id"]] = Resource.from_contents(document)
print(sorted(Counter("/".join(uri.split("/")[5:7]) for uri in schemas).items()))

bundle_schema = json.loads(Path("clinvar-gkm-1.2.0/schema/clinvar-gkm/clinvar-gkm-bundle.schema.json").read_text())
validator = Draft202012Validator(bundle_schema, registry=Registry().with_resources(schemas.items()))

# The first 100 records of each section: the whole delta takes about 17 minutes (see below)
part = {"schema_version": bundle["schema_version"]} | {
    section: dict(list(records.items())[:100]) for section, records in bundle.items() if isinstance(records, dict)
}
validate_bundle_schema(part, bundle_schema, validator=validator)  # raises BundleValidationError on a violation
print("valid:", sum(len(records) for records in part.values() if isinstance(records, dict)), "records")

broken = json.loads(json.dumps({"schema_version": "1.2.0", "scv": {scv["id"]: scv}}))
broken["scv"][scv["id"]]["direction"] = "sideways"  # not a VA-Spec direction
try:
    validate_bundle_schema(broken, bundle_schema, validator=validator)
except BundleValidationError as error:
    print(error)

[('cat-vrs/1.1.1', 16), ('clinvar-gkm/1.2.0', 76), ('gkm-core/1.3.0', 11), ('va-spec/1.1.0', 40), ('vrs/2.1.1', 26)]
valid: 1118 records
Bundle does not match its JSON Schema at scv/clinvar.submission:SCV008145211.1/direction: 'sideways' is not one of ['supports', 'neutral', 'disputes']

Records are validated as published, #/… pointers included, against the full ClinVar-GKM profiles. The 1,118-record slice takes about 30 seconds on one core; the whole delta, 39,062 records, validates in about 17 minutes (pass bundle instead of part).

The same schemas resolve by $id through w3id.org, so a registry can fetch them on demand instead of reading a local tree. The bundle schema itself can be fetched the same way, from https://w3id.org/clingen/schema/clinvar-gkm/1.2.0/clinvar-gkm-bundle.schema.json. Fetching makes one request per schema, so validate a slice, here the first 25 records of each section. This continues from the block above (bundle_schema, Resource, Draft202012Validator):

import functools

import requests


@functools.cache
def fetch(uri):
    return Resource.from_contents(requests.get(uri, timeout=30).json())


fetching = Draft202012Validator(bundle_schema, registry=Registry(retrieve=fetch))
part = {"schema_version": bundle["schema_version"]} | {
    section: dict(list(records.items())[:25]) for section, records in bundle.items() if isinstance(records, dict)
}
validate_bundle_schema(part, bundle_schema, validator=fetching)
print("valid:", sum(len(records) for records in part.values() if isinstance(records, dict)), "records;",
      fetch.cache_info().currsize, "schemas fetched")

valid: 293 records; 104 schemas fetched

validate_bundle_schema takes a whole bundle in memory. For multi-GB full bundles, the release used a streaming, multi-process wrapper around it; that wrapper is proposed for the toolkit, as gkm-validate-bundle, in ga4gh/gkm-starter-kit#128, which is not yet released. That wrapper takes hours on a full bundle (about 17 h on 64 cores for a 1.2.0 full), so the release validates every bundle with jsonschema-rs instead (src/scripts/validate-bundle.sh): the same bundle schema, registry and per-record document, in minutes. Its tests check that it fails the same records as the toolkit, and each version release also runs the toolkit on a sample of a full; see Release Validation.

Loading bundles¶

The toolkit's loader needs upstream updates for ClinVar-GKM bundles

The toolkit's loader tools (load_bundle, Bundle.resolve, Bundle.export and its model conversion) do not yet read ClinVar-GKM 1.1.0 or 1.2.0 bundles. They need updating upstream in two ways:

  1. The most recent GKM spec versions, which 1.1.0 and 1.2.0 data use: GKM-Core 1.3.0, VRS 2.1.1, Cat-VRS 1.1.1 and VA-Spec 1.1.0. ga4gh.gkm 0.4.1 matches these only through the pre-release libraries above, and it accepts a schema version only when it equals the installed library's.
  2. A way to handle producer-specific classes outside VA-Spec. The loader resolves schema references only against the GA4GH schemas it ships, cannot be given a producer's schemas, and converts records only to GA4GH model classes. ClinVar-GKM extends them in schema/clinvar-gkm/: the ten custom propositions (ClinvarAffectsProposition … ClinvarUndefinedProposition), ClinvarGeneContextQualifier, the statement profiles ClinvarScvStatement, ClinvarVcvStatement and ClinvarRcvStatement, the variant profile ClinvarCategoricalVariant (with ClinvarCanonicalAllele, ClinvarCategoricalCnvChange, ClinvarCategoricalCnvCount and ClinvarNonConstrainedVariant) and ClinvarSomaticEvidenceLine. load_bundle stops at the first of these references.

Until then, use the model libraries for the standard classes and plain JSON for the extended ones, as on this page. Related work: ga4gh/gkm-starter-kit#128.

From Parquet¶

The Parquet tables have no data column: every property of a record is its own typed column, named after the bundle property, and a reference is the bare id of the record it names, not a #/… pointer (see No data column). How close a row is to its bundle record decides how to get a model from it:

  • The VRS tables (allele, location, sequenceReference): a row without its NULL columns is the bundle record, with bare-id references, apart from the few columns noted below. It builds the model directly.
  • Every other table keeps values in a table's shape: extension values in value_<kind> slots, list references as {id, section} STRUCTs, a _section column beside a reference, some nested values as JSON text. Query those tables for what you need, then take the records themselves from the bundle.

Build Your Own Tables and Mini-Bundles covers gkm-bundle-parquet, the tool that builds the tables and cuts mini-bundles.

VRS records from rows¶

Read rows as dictionaries through pyarrow, drop the NULLs, and build the models (vrs is imported in VRS alleles and their identifiers). Here, the alleles of three variants: variation.members gives each member's id and the table it is in.

import duckdb

P = "https://data.clinvar-gkm.org/v1/1.2/parquet"


def strip_nulls(value):
    """A row, or a STRUCT or list inside it, without its NULL fields."""
    if isinstance(value, dict):
        return {k: strip_nulls(v) for k, v in value.items() if v is not None}
    if isinstance(value, list):
        return [strip_nulls(v) for v in value]
    return value


def rows(query, params=()):
    """Run a query; return each row as a dict of column name to value, without NULLs."""
    table = duckdb.execute(query, list(params)).to_arrow_table()
    return [strip_nulls(row) for row in table.to_pylist()]


def by_id(table, ids, columns="*"):
    """Fetch the rows of one table whose id is in ids, keyed by id."""
    marks = ", ".join("?" * len(ids))
    query = f"SELECT {columns} FROM '{P}/{table}.parquet' WHERE id IN ({marks})"
    return {row["id"]: row for row in rows(query, ids)}

To load these records into the library models, take them from the bundle the tables were built from: the weekly full of the manifest's source_release, which is weekly/clinvar-gkm_00-latest_weekly.json.gz while the tables are current. gkm-bundle-parquet select cuts a mini-bundle from it: the SCV and every record it points to, directly or through other records, so every pointer in it resolves inside the file.

select reads the whole bundle, 4.9 GB compressed, so download it once and pass the local path; --full also takes a URL, but then streams the whole file on every run. uvx comes with uv; without it, pip install gkm-bundle-parquet==2.0.0 and run gkm-bundle-parquet in its place. --out must not exist yet: delete it to run again.

curl -fO https://data.clinvar-gkm.org/v1/1.2/weekly/clinvar-gkm_00-latest_weekly.json.gz
uvx gkm-bundle-parquet@2.0.0 select \
    --full clinvar-gkm_00-latest_weekly.json.gz \
    --bundle-schema https://w3id.org/clingen/schema/clinvar-gkm/1.2.0/clinvar-gkm-bundle.schema.json \
    --driver scv --ids clinvar.submission:SCV001142520.1 --out SCV001142520.json.gz

One id costs about as much as many: pass every id you need in one run (--ids takes a comma-separated list, --ids-file a file of ids). Remote reads of big tables are slow

The tables are sorted by id, and each row group's id range is in the file footer, so a lookup by id reads only the row groups that can hold it. A filter on any other column (scv.proposition above) reads that column from every row group, one HTTP request each, and the CDN limits each client to about 55 requests per 10 seconds. For anything beyond a handful of lookups, download the tables you need and query them locally (Working at Scale).

Round trip¶

model_dump(mode="json", exclude_none=True) serializes a model back to JSON. Records carry no null fields (except the open bound of a VRS Range, which survives), so exclude_none=True loses nothing. Compare every record of the delta with its round trip (this uses vrs, catvrs and va from the blocks above):

from collections import Counter

from ga4gh.core.models import MappableConcept

    "sequenceReference": vrs.SequenceReference, "location": vrs.SequenceLocation, "allele": vrs.Allele,

def model_for(section, record):
    if section.startswith("proposition"):

Large bundles¶

A full bundle is about 4.9 GB compressed and 68.5 GB decompressed, so a json.load of one does not fit in a laptop's memory. Three ways to work with it:

  • Stream it. ijson reads one record at a time; kvitems(f, "scv") yields each (id, record) of a section. Build a model per record, keep what you need, and memory stays flat. One pass reads the whole file.
  • Query the Parquet for the latest release to find the records you need, and cut just those out of the bundle with gkm-bundle-parquet select, as above.
  • Cut a sub-bundle. The Sub-Bundle Extraction tool, which made the 1.1.0 sample sub-bundle, extracts a self-contained bundle for a list of statements. It reads the project's BigQuery tables, not a published file, so it needs access to those datasets.

Streaming the delta's scv section, for example, to count classifications (gzip, Counter and va are imported above):

import ijson

classifications = Counter()
with gzip.open("clinvar-gkm-delta_2026-1115.json.gz", "rb") as f:
    for scv_id, record in ijson.kvitems(f, "scv", use_float=True):
        classifications[va.Statement(**record).classification.name] += 1
print(sum(classifications.values()), classifications.most_common(4))

17562 [('Uncertain significance', 7388), ('Likely benign', 3389), ('Pathogenic', 2242), ('Likely pathogenic', 1986)]
