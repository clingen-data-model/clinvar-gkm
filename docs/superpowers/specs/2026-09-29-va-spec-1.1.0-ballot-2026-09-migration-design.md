# VA-Spec 1.1.0-ballot.2026-09 migration — Design

> **Status:** design (drafting 2026-09-29). Branch `feat/va-spec-1.1.0-ballot-2026-09`.
> Migrates clinvar-gkm from va-spec `1.1.0-ballot.2026-07.2` (current submodule) to
> `1.1.0-ballot.2026-09.1` (branch `origin/1.1.0-ballot.2026-09`), the next official VA-Spec release.
> Goal: emit output that **validates** against the 2026-09 va-spec JSON schemas.
> This spec **partially reverses** the `2026-08-12-custompropositions-conformance-and-delivery-grouping`
> design — the `CustomProposition` mechanism it targeted is deleted upstream.

## Decisions locked (2026-09-29)

1. **Community-profile scope = Statement types only.** Adopt the profile *Statement* classes
   (`VariantPathogenicityStatement` for germline, `VariantClinicalSignificanceStatement` for AAC/somatic)
   so classification+strength validate under the profiles; do **not** synthesize per-criterion
   EvidenceLines (ClinVar does not reliably carry ACMG PVS1/PS/… or AMP-tier criterion codes). → **Phase 2.**
2. **Custom ClinVar\*Propositions = bespoke subtypes of the open base.** Emit the real `type` name
   (`type:"ClinvarAffectsProposition"`, …); redefine each `schema/clinvar-gkm/json/Clinvar*Proposition`
   as a subtype of the now-**open, abstract** `va-spec:SubjectVariantProposition`, and validate against it.
3. **Qualifiers = typed fields.** Use the same typed qualifier fields as the standard propositions
   (`geneContextQualifier`, `alleleOriginQualifier`, `modeOfInheritanceQualifier`, `penetranceQualifier`)
   on the custom subtypes — retire the generic `qualifiers[]` `{name,value}` array.
4. **Rollout = phased, oracle-gated PRs.** Phase 1 (core conformance) lands and is oracle-verified
   (`0,0,0`) before Phase 2 (profile adoption).

## Success criteria

- `submodules/va-spec` at `1.1.0-ballot.2026-09.1`; all `schema/` symlinks + `$id`/`$ref` resolve.
- A representative sample of emitted **propositions, statements, and evidence lines** validates against
  the 2026-09 `schema/va-spec/json/*` and `schema/clinvar-gkm/json/*` (statements/ELs are currently
  unvalidated — see §5).
- Reconstruction oracle = `0,0,0` on all sections **after** accounting for the intended, one-time value
  churn (every proposition's JSON changes due to the field renames — expected, not a regression).

## 0. Upstream change summary (what the 2026-09 ballot does)

Verified by `git -C submodules/va-spec diff 1.1.0-ballot.2026-07.2 origin/1.1.0-ballot.2026-09`.

**Cross-cutting**
- Schema tree flattened: `schema/va-spec/base/json/<Class>` → `schema/va-spec/json/<Class>` (the `base/`
  layer is gone). Community profiles moved to `schema/va-spec/json/{acmg-2015,aac-2017,ccv-2022}/`.
- Core dep renamed + bumped: `gks-core/1.2.0-ballot.2026-07.1` → **`gkm-core/1.3.0-ballot.2026-09.1`**;
  VRS `2.1.0…` → `2.1.1-ballot.2026-09.1`; Cat-VRS `1.1.0…` → `1.1.1-ballot.2026-09.1`.
- `$id` prefix drops `/base/`; test namespace `va-spec.base` → `va-spec`.
- **Build toolchain renamed + bumped:** the schemas are generated by the GA4GH metaschema processor, now **`ga4gh.gkm.metaschema==0.4.8`** (was `ga4gh.gks.metaschema==0.3.2`; repo `ga4gh/gkm-metaschema`). Same CLI (`source2classes`/`source2splitjs`/`y2t`), but the source-YAML DSL changed — the new va-spec sources declare base classes with `inherits:`+`abstract:` and compose profiles via inline `allOf:[$refCurie: base, {properties: …}]` (no `protectedClassOf`/`…Properties` `$defs`). clinvar-gkm's four `*-source.yaml` files + `.requirements.txt` + `y2md.py` import must track this.

**Propositions**
- **`CustomProposition` is deleted** (class + schema + fixture). New pattern: give the object its own
  `type` name and validate against the now-**open, abstract** `Proposition` / `SubjectVariantProposition`
  (no `additionalProperties:false` on those bases → extra typed fields tolerated).
- **All proposition subject/object slots unified**: `subjectVariant`→`subject`; and
  `objectCondition`/`objectTumorType`/`objectTherapy` **all collapse to a single `object`**
  (`Condition|ConditionSet|iriReference` for condition/tumor semantics). Qualifier fields keep their
  typed names. `VariantTherapeuticResponseProposition` now **requires `conditionQualifier`**.

**Statements & EvidenceLines** (both closed leaves — `additionalProperties:false`)
- New abstract root `InformationEntity` → {`Statement`, `EvidenceLine`, `StudyResult`, `DataItem`}.
- `EvidenceLine.hasEvidenceItems` widened to `InformationEntity|iriReference` — it now carries **both**
  standard evidence (Statement/StudyResult/DataItem) **and** nested EvidenceLines. Target link is
  **`targetProposition`** (`Proposition|iri`).
- `Statement`: adds `hasEvidence` (Statement/StudyResult/DataItem — **excludes EvidenceLine**) for raw
  cited evidence; keeps `hasEvidenceLines` (EvidenceLine|iri) for scored arguments; adds `quality`,
  `score`; **`direction` no longer required** (`required: [proposition, type]`).

**Community profiles** (Phase 2): `acmg-2015` = `VariantPathogenicityStatement`/`…EvidenceLine`;
`aac-2017` = `VariantClinicalSignificanceStatement`, `AmpAscoCapEvidenceLine` (+Diagnostic/Prognostic/
Therapeutic); `ccv-2022` = oncogenicity. Strict `methodType`↔code coupling; "not-met ⇒ neutral, no
strength" rule. Profile *Statement* enums are guideline-specific (strength/classification vocab + system
const + `specifiedBy` required).

## Phase 1 — Core conformance (required, consumer-breaking)

### 1. Cross-cutting mechanical migration

**1.1 Submodule bump.** `submodules/va-spec` → `1.1.0-ballot.2026-09.1`, including nested
`cat-vrs`/`vrs`/`gkm-core`. Confirm the `schema/` symlinks (`schema/va-spec`, `schema/cat-vrs`,
`schema/vrs`) still resolve; **add `schema/gkm-core`** and retire `schema/gks-core` (the symlink name +
any references).

**1.2 clinvar-gkm schema source refs.** Every `$ref`/import in `schema/clinvar-gkm/*.yaml` (and the
generated `json/*`) points at `.../va-spec/1.1.0-ballot.2026-07.2/base/json/...`,
`.../gks-core/1.2.0-ballot.2026-07.1/...`, `vrs/2.1.0…`, `cat-vrs/1.1.0…`. Update to:
`va-spec/1.1.0-ballot.2026-09.1/json/...`, `gkm-core/1.3.0-ballot.2026-09.1/...`, `vrs/2.1.1…`,
`cat-vrs/1.1.1…` (note `/base/` removed). Then `cd schema/clinvar-gkm && make` to regenerate; commit only
the semantic diff (metaschema emits `$defs` in set order — canonical-diff to filter reorder churn; ref
ga4gh/gks-metaschema#63).

**1.3 clinvar-gkm schema version bump (decision).** The `$id` version is `1.0-rc3`. This release is
consumer-breaking (field renames) → bump to `1.0-rc4` (or `1.0.0`). **Open — confirm target version.**

**1.4 Validator path-routing fix** (`src/scripts/validate-schema-conformance.py`). Two fragile
assumptions break under the reorg: (a) schema discovery only descends dirs literally named `json`
(`load_registry`, ~L76) — the flattened + per-profile layout is still under `json/` dirs, OK, but verify;
(b) routing is by **bare filename, first-wins** (`name2contents.setdefault`, ~L93 / `schema_name_for`
~L98-105) — with profiles, same-named classes can now exist across `json/` and profile dirs and silently
shadow. Make routing **path-aware** (namespace-qualified) and drop the `customPropositionType` route
(§2). `relax_additional_properties` (~L40-61) still needed for closed-world `allOf`.

### 2. Propositions — rename + custom recreation (the priority)

**2.1 Uniform rename (all proposition types, all 3 levels).** `subjectVariant` → `subject`;
`objectCondition`/`objectTumorType`/`objectTherapy` → **`object`**. This *removes* the object-field
divergence the prior spec (§3.5) had to special-case — Oncogenicity and TherapeuticResponse targets now
just use `object`. Keep typed qualifier fields as-is.

**2.2 Drop the CustomProposition shape.** Stop emitting `type:"CustomProposition"` +
`customPropositionType`. Emit the real `type` (`ClinvarAffectsProposition`, `ClinvarRiskFactorProposition`,
… all 10 incl. `ClinvarUndefinedProposition`) directly. Predicate map is unchanged (the CASE at
`gkm-vcv-statement-proc.sql` ~L516-530, duplicated ~L554-568 / ~L592-606; SCV ~L204-214). Retire the
generic `qualifiers[]` array; emit typed `geneContextQualifier`/`modeOfInheritanceQualifier`/
`penetranceQualifier` (SCV only, only when present) matching the standard shape.

**2.3 Schema rework** (`schema/clinvar-gkm/clinvar-proposition-source.yaml`):
- `ClinvarGermlineCustomProposition`: re-base `allOf` from deleted `va-spec:CustomProposition` →
  **`va-spec:SubjectVariantProposition`** (open). Replace the generic `qualifiers[]` `$def` with the
  typed qualifier fields; `subject`/`object` now inherited from the open base (verify the narrowing:
  `object` = `Condition|ConditionSet|iri`).
- Each `Clinvar*Proposition`: keep the `type` const = its own name (drop `customPropositionType`), keep
  the `predicate` const. `ClinvarProposition` union `oneOf` refs update to the new va-spec `json/` paths.
- These remain **open** subtypes (no `additionalProperties:false`), which is what makes them valid
  against the open base while carrying ClinVar-specific typed qualifiers.

**2.4 VCV object cardinality (carry-over from prior spec §3.5 #1 — still required).** VCV emits
`agg.unique_conditions` (an **array**) as the object across all 3 layers; the schema wants a **single**
`Condition|ConditionSet|iri`. Fix: emit a single **`ConditionSet`** pointer when >1 member, a bare
**`Condition`** when exactly 1 (mirroring RCV/SCV). Reconcile `parquet-schemas/vcv_proposition`-side and
the `rcv_proposition.sql` `JSON_VALUE_ARRAY` extractor to single.

**2.5 `conditionQualifier` now required on TherapeuticResponse.** The somatic **target** props already
emit `objectTherapy`+`conditionQualifier` per the prior spec; after the `object*→object` rename, **verify
`conditionQualifier` is present** on every `VariantTherapeuticResponseProposition` (now in `required`), or
validation fails.

**2.6 Pipeline emission** — three procs (`gkm-scv-statement-proc.sql` ~L546-572 subject-prop shape /
~L204-214 type; `gkm-vcv-statement-proc.sql` ~L508-534 ×3 layers; `gkm-rcv-statement-proc.sql`
analogous). Keep the wide-struct + `JSON_STRIP_NULLS(remove_empty=>TRUE)` idiom; the `is_custom` branch
now only toggles open-vs-closed qualifier handling, not the field *names* (subject/object are uniform).

**2.7 Downstream coordination.** `parquet-schemas/{varcond,vartumor,vartherapy,varcustom}-proposition.sql`
+ the group split in `export-gkm-dicts.sh` (~L94-105, ~L198-201): read `type`/`subject`/`object`
(drop `customPropositionType`/`subjectVariant`/`objectCondition`). Bundle `SECTIONS` names
(`assemble-gkm-dicts.py` ~L68-87) unchanged. Delta: full one-time churn of every proposition record
(intended).

### 3. EvidenceLines — restructure

**3.1 Aggregate ELs: `evidenceItems` → `hasEvidenceItems`.** VCV/RCV aggregate evidence lines
(`gkm-vcv-statement-proc.sql` ~L415-497; `gkm-rcv-statement-proc.sql` ~L462-540) hold an array of
**lower-layer Statement pointers** under `evidenceItems`. Statements are `InformationEntity`, so those
refs are valid items — this is a **straight property rename** to `hasEvidenceItems`. Update
`parquet-schemas/{vcv,rcv}_evidenceLine.sql` (`evidenceItems` column) + the `evidenceLine` bundle merge
(`assemble-gkm-dicts.py` ~L83). No EL-under-EL nesting exists today and none is introduced in Phase 1;
the current chain (Statement → `hasEvidenceLines` → EL → `hasEvidenceItems` → lower Statements) maps
cleanly onto the 2026-09 model.

**3.2 Somatic EL: `proposition` → `targetProposition`.** The SCV somatic EL
(`gkm-scv-statement-proc.sql` ~L864-942) emits a bespoke **`proposition`** field; va-spec EvidenceLine's
property is **`targetProposition`** (`Proposition|iri`). Rename in the proc + `parquet-schemas/
evidenceLine.sql` (`proposition_id`). Rewrite the bespoke `schema/clinvar-gkm/json/ClinvarSomaticEvidenceLine`
to simply **narrow the native `targetProposition`** to the 3 somatic types (+iri) — its current extra
`proposition`/`evidenceOutcome` `$def` is redundant (both are native to va-spec EvidenceLine now) and, on
a closed leaf, non-conformant.

### 4. Statement conformance

- va-spec `Statement`/`EvidenceLine` are **closed leaves**. The bespoke `Clinvar{Scv,Vcv,Rcv}Statement`
  schemas may only **narrow** (no added top-level properties beyond what va-spec defines) — audit and
  remove any added fields, or move them to `extensions`.
- `direction` optional now: no emission change needed, but any downstream code assuming `direction` is
  always present must null-check.
- clinvar-gkm continues to use `Statement.hasEvidenceLines` (not the new `Statement.hasEvidence`) — no
  change; `hasEvidence` is available if we later want to cite raw evidence without an EL wrapper.

### 5. Validation + oracle gate (Phase 1 exit)

- Extend `validate-schema-conformance.py` to also validate **Statements and EvidenceLines** (currently
  skipped) against the 2026-09 schemas — this is the gate that catches the renames and stray fields.
- Structural checks in `validate-proposition-conformance.sh`: drop the `CustomProposition`↔
  `customPropositionType` assertions; add "`type` ∈ known Clinvar\*/Variant\* set", "single `object`",
  "`subject`/`object` present".
- Reconstruction oracle (`oracle-delta-reconstruction.sh`) must be `0,0,0` on all sections after the
  intended value churn is accounted for (diff shows only renamed fields + reshaped custom props).

## Phase 2 — Community profile Statement types (acmg-2015, aac-2017)

**Scope (locked): Statement types only, applied selectively.** Tag a statement with a profile Statement
type only when the SCV's assertion method indicates the guideline was used — do **not** blanket-apply
(profile Statement schemas assert guideline conformance: guideline-specific strength/classification
vocab, a `system` const, and `specifiedBy` required).

- **Germline** `VariantPathogenicityProposition` statements → `VariantPathogenicityStatement` (acmg-2015)
  where assertion method = ACMG 2015. Requires: `classification` ∈ {pathogenic, likely pathogenic, benign,
  likely benign, uncertain significance} (+ ClinGen low-penetrance/risk-allele set); `strength` ∈
  {definitive, likely} with system const "ACMG Guidelines, 2015"; `classification`+`specifiedBy` required.
- **Somatic** `VariantClinicalSignificanceProposition` statements → `VariantClinicalSignificanceStatement`
  (aac-2017) where assertion method = AMP/ASCO/CAP 2017. Requires: `classification` ∈ {tier i…iv},
  `strength` ∈ {strong, potential}, tier→direction rules (Tier III neutral, Tier IV disputes, no strength).

### Phase 2 open questions (resolve when Phase 2 is planned in detail)

1. **Qualifying signal** — which `AssertionMethod` values (currently free text in `specifiedBy.name`)
   map to ACMG-2015 / AMP-ASCO-CAP-2017? Need an authoritative mapping (upstream or a curated list).
2. **Coding conformance** — clinvar-gkm's `classification`/`strength` `primaryCoding` come from upstream
   `clinvar_clinsig_types`; the profile enums + `system` consts must match exactly or validation fails.
   Determine whether to remap codings or gate profile-typing on already-conformant codings.
3. **`hasEvidenceLines` restriction** — profile Statements restrict `hasEvidenceLines` to the profile EL
   type (or iri). Our aggregate ELs are referenced by iri, which satisfies the schema branch — confirm.
4. **Delivery** — do profile-typed statements change the `scv`/`vcv`/`rcv` bundle sections or add a
   discriminator column? Coordinate with the delta model.

*(Profile per-criterion EvidenceLines — `VariantPathogenicityEvidenceLine`, `AmpAscoCapEvidenceLine` — are
explicitly out of scope: ClinVar lacks the structured criterion codes. Revisit only if upstream supplies
them.)*

- **Submodule/symlinks:** `submodules/va-spec` bump; `schema/gkm-core` symlink (retire `gks-core`).
- **Build toolchain:** `.requirements.txt` (`ga4gh.gks.metaschema==0.3.2`→`ga4gh.gkm.metaschema==0.4.8`),
  `schema/clinvar-gkm/y2md.py` import; the four `*-source.yaml` files migrated to the 0.4.8 DSL idiom
  (`protectedClassOf`→inline `allOf:[base,{properties}]`).
- **Schema:** `schema/clinvar-gkm/*.yaml` (proposition + statement sources — ref bumps, `object*`→`object`,

  vcv_evidenceLine,rcv_evidenceLine}.sql`.
- **Bundle:** `assemble-gkm-dicts.py` (section list unchanged; verify pointer prefixes).
- **Validation:** `validate-schema-conformance.py` (path-aware routing + validate Statements/ELs),
  `validate-proposition-conformance.sh` (assertions updated).
- **Docs:** proposition/statement/evidence-line class + pipeline pages; propositions predicate table
  (also fix the `hasClinicalSignificanceFor` vs docs `isClinicallySignificantFor` drift).
- **ADR:** add `docs/decisions/0004-va-spec-2026-09-migration.md` capturing the four locked decisions.

## Rollout (phased, oracle-gated)

- **PR 1 (Phase 1a):** submodule bump + symlink/ref/path updates + schema regen + validator path fix.
  Gate: schemas resolve, existing validation still green.
- **PR 2 (Phase 1b/c):** proposition rename+custom recreation, VCV object single, EvidenceLine renames,
  Statement audit; validator extended to Statements/ELs. Gate: sample validates `0` failures;
  reconstruction oracle `0,0,0` (intended churn accounted). *(1b and 1c may split further if review
  surface is large.)*
- **PR 3+ (Phase 2):** profile Statement typing, after Phase-2 questions resolved. Each PR oracle-gated.

## Risks / watch-items

- **Metaschema processor upgrade is a hard dependency:** the schema build requires `ga4gh.gkm.metaschema==0.4.8`
  and its changed source-YAML DSL. The exact set of DSL edits to the clinvar `*-source.yaml` files (chiefly
  `protectedClassOf`→inline `allOf:[base,{properties}]`) can only be confirmed by running `make` under 0.4.8 —
  the first clean build is the schema checkpoint.
- **One-time full delta churn** on every proposition (field renames) — expected; make it explicit in the
  release notes so consumers aren't surprised.
- **Closed-leaf `allOf` composition** for bespoke Statement/EL types can be unsatisfiable under strict
  validators; the validator's `relax_additional_properties` handles it, but genuine extra fields must go
  to `extensions`.
- **gks-metaschema non-deterministic `$defs` ordering** — canonical-diff on regen (ga4gh/gks-metaschema#63).
- **Consumer breakage** — `gks-core`→`gkm-core`, `/base/` path removal, and `subjectVariant`/`objectCondition`
  → `subject`/`object` all change the published contract; coordinate the announcement with the release.
