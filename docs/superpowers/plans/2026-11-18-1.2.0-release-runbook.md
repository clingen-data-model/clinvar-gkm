# ClinVar-GKM 1.2.0 release: runbook

> **Status:** prepared 2026-11-18; decisions D1–D6 approved 2026-11-18; step 1 done (#225 merged, 788ef82). Steps marked **[OK]** touch BigQuery, GCS/GCP, live R2,
> Cloudflare, a tag, a merge, or an email, and run only after the maintainer confirms that step. Never touch live R2
> without that confirmation; dry-run first wherever a script offers it. Never print the R2 or Cloudflare credentials.

**Scope.** 1.2.0 = the narrowed profiles (#215, on `main`) plus the aggregate VCV/RCV `primaryCoding`, strength and
direction fixes (#225, fixes #202, #226, #227). As a MINOR it opens a new R2 line, **`v1/1.2/`** (ADR 0009 §1, §5),
and freezes **`v1/1.1/`** (ADR 0008 (b), (c)). Maintainer decisions of 2026-11-18:

1. `v1/1.2/` starts with **one checkpoint monthly** (the first 1.2.0 full) plus deltas forward. No republish of history.
2. At the freeze, `v1/1.1/` **loses its weekly fulls and its `parquet/`**; its monthlies, `00-latest`, archive and
   deltas stay, frozen forever, no `eol`.
3. Superseded lines are frozen forever.
4. Parquet publishing stays on hold (`--skip-parquet`) until #217 lands with `gkm-bundle-parquet` 2.0.0.

Tooling (PR "feat(r2): v1/1.2 line, checkpoint bootstrap and line freeze"): `r2_layout.LINES` / `CURRENT_LINE`,
`R2_LINE` defaults `v1/1.2/`, `run-release.sh --bootstrap-monthly=YYYY-MM`, the first-delta chain check in
`r2_layout.py patch-manifest`, and `r2-freeze-line.sh` (dry run by default).

## Decisions (approved 2026-11-18)

- **D1. The checkpoint: `v1/1.2/clinvar-gkm_2026-11.json.gz` ← 2026-10-31**, rebuilt with the 1.2.0 procs. It is the
  ADR 0002 monthly for 2026-11, so the label is honest, and the two lines meet at the same ClinVar state. The 1.2
  deltas then run 2026-11-08, 2026-11-15, … (never published in 1.1). The docs examples in this PR assume it.
- **D2. Yes: a final 2026-11 monthly in `v1/1.1/`**, a server-side copy of the 1.1 weekly full 2026-10-31 (no
  build, no BigQuery), done from the `1.0` code **before** step 4 rebuilds 2026-10-31 and before the freeze deletes
  the weekly (step 2). The automated announcement is accepted: within about 2 h, `announce-monthly.yml` emails the
  list and posts a Discussion for 2026-11 (1.1 line, digest 10-04..10-31). That also keeps the 1.2 checkpoint from
  being auto-announced (2026-11 is then in `announced.json`).
- **D3. Freeze with `--keep-parquet`** (step 9), and run the freeze again without it once `v1/1.2/parquet/` is
  published (step 13). The data stays, but from step 8 the DuckDB console follows the root index to `v1/1.2` and
  is **empty until the 1.2 Parquet set is published**: there is no console change, so run step 13 immediately
  after step 8. With #217 based on `release/1.2.0` (merging it needs the maintainer's OK), Parquet ships with
  1.2.0.
- **D3 amended 2026-11-19 (cutover dates):** publish Friday 2026-11-20 (advance notice that morning → steps 7, 8,
  13's build and upload), and run step 9 **once, without `--keep-parquet`, on Monday 2026-11-23**, so the notice
  gives users three days to save the 1.1 weekly fulls and Parquet. Until then `v1/1.1/` is `frozen` in the root
  index but still holds them.
- **D4. #229 merges to `main` after #228** (versioned docs). Its pages, which give `v1/1.2/` URLs that 404 until
  step 8, then show only on `dev`, not in the released `1.1` docs.
- **D5. No 1.1 weeklies for November.** 2026-11-08 and later become the first 1.2 deltas.
- **D6. ADR amendment in the release PR.** ADR 0009 §1 says nothing is deleted from a frozen line, and ADR 0008 (b)
  describes a new line built in full. D1 and D2 + the freeze change both; the amendment goes in the release PR
  (step 3).

## Steps

Gate checks follow each step. "Rollback" says how to undo it.

### 0. Pre-flight (read-only)

- [ ] **No release on the `1.0` branch until step 3 has merged `main` into it** (no `1.0.x` or other tag published
      as a GitHub Release from `1.0`). The `release: published` event runs the workflow file *at the tag*; `1.0`
      still has the old whole-site `deploy-docs.yml`, which builds the tag's docs and publishes them with
      peaceiris without `keep_files`. That would replace all of `gh-pages`: `1.1/`, `dev/`, `versions.json` and
      the root redirects would be gone, and the site would serve the `1.0` tree's unversioned docs (the pre-1.1
      `v1/datasets/…` URLs, which 404). Recovery would be a dispatch of `dev` and of `1.1`. A tag pushed without a
      GitHub Release doesn't trigger the workflow, but don't push one either: it is a release tag in name.
- [ ] **The release tag's docs must describe the line being shipped.** Root cause of the 2026-11-19 docs
      incident: `1.1.0` was tagged on `1.0` without `main`'s 1.1.0 docs, so the tag's pages gave the pre-1.1
      `v1/datasets/…` URLs and no 1.1.0 changelog section; the `1.1` docs are now built from `main@036bec2`
      instead (`src/scripts/docs-line-sources.txt`, ADR 0011 §6). For 1.2.0, step 3 merges `main` into the
      release branch; before the tag (step 7), check on `origin/1.0`: `git grep -l 'v1/1\.2/' origin/1.0 -- docs`
      lists the download pages, `git grep -l 'v1/datasets' origin/1.0 -- docs ':!docs/superpowers'` is empty, and
      `docs/reference/changelog.md` has the `## 1.2.0 — <date>` section.
- [ ] `gh pr view 225 --json state,mergeable`; CI green; #225 body: scratch rebuild 0,0,0.
- [ ] `bq ls --max_results=100000 | grep -E 'clinvar_2026_1[01]_'`: the datasets after 2026-10-31 and their
      version suffix; confirm 2026-10-31's suffix (e.g. `v2_6_1`), and that no dataset dated 11-01..11-04 has
      `gkm_pipeline_version` (else D1's source changes).
- [ ] `curl -s https://data.clinvar-gkm.org/v1/1.1/index.json`: `latest_release` still 2026-10-31, no 2026-11
      monthly; `curl -sI .../v1/1.2/index.json` is 404 (the line is empty).
- [ ] `src/scripts/r2-freeze-line.sh v1/1.1/` (dry run, read-only listing): no `PROBLEM`; keeps 41 files.
- [ ] Cost quote for steps 4–5 (BigQuery): the full procs on 2026-10-31 plus each catch-up release; announce it.

### 5. Build the first 1.2.0 full and the first delta (no upload) **[OK: BigQuery spend]**

The proc gate key changed, so the checkpoint is a full proc rebuild. vrsify is unchanged, so start at stage 4:

```bash

```

`--dry-run` runs stage 4 for real (BigQuery) and only prints stage 5: it checks the line is `empty`, that ClinVar's
2026-11 source is 2026-10-31, and prints the build and upload it would do. Then stage the bundle:

```bash
src/scripts/release-gkm.sh 2026-10-31 <ver> --month-label=2026-11 --no-upload     # export, assemble, rs-validate

# toolkit as a sample of 1.2.0 records, NEVER published (it has no monthly to replay onto in v1/1.2/)

```

Gate ("validate"): `validate-bundle.sh <full> --engine rs` = 0 failures (release-gkm.sh runs it); the delta's toolkit
validation = 0 failures (release-gkm-delta.sh runs it); the full carries `"schema_version": "1.2.0"` and the #225
fields (a VCV aggregate classification with `primaryCoding` in the staged full). The first publishable 1.2 delta
(2026-11-08, baseline 2026-10-31) is built and toolkit-validated by its own run in step 8, before anything uploads.
