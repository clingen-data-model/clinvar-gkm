# VA-Spec 1.1.0-ballot.2026-09 Migration — Phase 1 (Core Conformance) Implementation Plan

> **For agentic workers:** REQUIRED: Use superpowers:subagent-driven-development (if subagents available) or superpowers:executing-plans to implement this plan. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make clinvar-gkm output validate against the va-spec `1.1.0-ballot.2026-09.1` JSON schemas — bump the submodule, update all schema refs (`gks-core`→`gkm-core`, drop `/base/`, version bumps), collapse every proposition to the unified `{type, subject, predicate, object, …typed qualifiers}` shape (deleting the `CustomProposition`/`customPropositionType` model), recreate the 10 `Clinvar*Proposition` types as subtypes of the open `SubjectVariantProposition` base with typed qualifiers, rename `evidenceItems`→`hasEvidenceItems` and the somatic EL's `proposition`→`targetProposition`.

**Architecture:** The 2026-09 ballot unifies all proposition subject/object slots (`subjectVariant`→`subject`; `objectCondition`/`objectTumorType`/`objectTherapy`→`object`) and deletes `CustomProposition`. This *collapses* the current per-type divergence: the `is_custom` 3-way `object` branch, the `subjectVariant`/`subject` split, and the generic `qualifiers[]` array all disappear — every proposition emits `{type:<real gks_type>, id, subject, predicate, object[, geneContextQualifier, modeOfInheritanceQualifier, penetranceQualifier]}`. The 4 delivery groups (`varcond`/`vartumor`/`vartherapy`/`varcustom`) and the `#/<group>-proposition/<id>` pointer scheme are unchanged (the group is derived from `gks_type`, not the field name). EvidenceLine nesting maps cleanly: `EvidenceLine.hasEvidenceItems` (renamed from `evidenceItems`) still holds lower-layer Statement pointers (Statements are `InformationEntity`, a valid item type); the somatic EL uses the native `targetProposition`.

**Tech Stack:** BigQuery stored procedures (`bq`, project `clingen-dev`); GA4GH **gkm-metaschema** processor (`ga4gh.gkm.metaschema==0.4.8`; CLI `source2classes`/`source2splitjs`/`y2t`) via `cd schema/clinvar-gkm && make` for schema regen; Python 3.12 for validation; git submodules; `jq` for canonical diffs.

**Spec:** `docs/superpowers/specs/2026-09-29-va-spec-1.1.0-ballot-2026-09-migration-design.md`. **Phase 2 (community-profile Statement types — acmg-2015/aac-2017) is a separate later plan — NOT in scope here.**

**Branch:** `feat/va-spec-1.1.0-ballot-2026-09` (already created off `main`). Deploy a proc: `bq query --project_id=clingen-dev --use_legacy_sql=false < src/procedures/<file>.sql`. Call it: `CALL \`clinvar_ingest.gkm_<x>_statement_proc\`(DATE '<date>', FALSE);`.

**Conventions:**
- Commits must NOT contain "Generated with Claude Code"/"Co-Authored-By".
- `cpt.gks_type` is an **upstream** column — do NOT rename it (per `.claude/rules/sql-procedures.md`).
- Schema regen: commit only semantic changes — the metaschema emits `$defs` in non-deterministic order; canonical-diff (`diff <(git show HEAD:<f>|jq -S .) <(jq -S . <f>)`) to drop reorder churn.
- The schema build depends on **`ga4gh.gkm.metaschema==0.4.8`** (Chunk 2) — the exact source-YAML DSL edits can only be confirmed by running `make` under 0.4.8; iterate against its errors.
- Set `DS` to an available test dataset first: `bq ls --project_id=clingen-dev | grep clinvar_2026_08` — this plan uses `DS=clinvar_2026_08_16_v2_5_0` as the example (confirm it exists; else pick the latest).
- **Conformance only holds once Chunks 1–5 all land** (schema rename + proc rename are coupled). Do NOT cut a release from this branch mid-migration. Land Phase 1 as one PR (or a tightly-stacked set) with the oracle gate at the end (Chunk 7).
