## (a) GitHub Release body

**Title:** `1.2.0`

**Body:**

ClinVar-GKM **1.2.0** narrows the ClinVar profiles to exactly what the pipeline writes, adds a coding to every VCV
and RCV aggregate classification, fixes the aggregate `strength` and `direction`, and starts a new data line,
`v1/1.2/`. The bundle schema moves `1.1.0 → 1.2.0`, a MINOR release. From 1.2.0 the Parquet tables are built from
the bundle by `gkm-bundle-parquet` 2.0.0, with a new table layout.

### Schema 1.2.0: the ClinVar profiles describe exactly what the pipeline writes

Every bundle section now points at a ClinVar profile of its GA4GH class that allows exactly what the pipeline
writes (#215, #221):

- **What the pipeline never writes is forbidden**: 204 inherited properties are set to `false`.
- **What it always writes is required**, for example `id` on every record that has one.
- **Every pointer is limited to the sections it can target** (34 pointers).
- **Values the pipeline fixes are enumerated**, and every extension is a closed class with a constant `name`.
- **Section keys match the full id the pipeline builds**, not only its prefix.
- **New draft classes:** `ClinvarCopyNumberChange`, `ClinvarCategoricalCnvChange`, `ClinvarCategoricalCnvCount`,
  `ClinvarCopyChangeConstraint`, `ClinvarVariantClinicalSignificanceProposition`.

The data does not change for this: relabelled as 1.2.0, every record of the 2026-10-31 full bundle (91,854,927)
and delta validates with no failures. If you write your own records to these schemas, a property, value, pointer
or key form that 1.1.0 accepted but the pipeline never writes now fails.

### VCV and RCV classifications carry a coding (#202)

Every VCV and RCV statement's `classification` gains a `primaryCoding` (`code`, `system`), as SCV classifications
already have (#225):

- a label that is one classification term has the coding its SCVs carry, with the code in lower case
  (`Pathogenic` → `pathogenic` / `ACMG Guidelines, 2015`);
- a somatic clinical impact label is coded by its tier (`Tier I (Strong) for 2 tumor types` → `tier 1` /
  `AMP/ASCO/CAP (AAC) Guidelines, 2017`);
- any other label is a ClinVar-defined term, system `ClinVar`, code = the lower-cased label.

Over the 2026-10-31 release (21,309,008 VCV and RCV records):

| system | records |
| --- | ---: |
| ACMG Guidelines, 2015 | 20,147,326 |
| ClinVar, terms from ClinVar's lookup (p/lp, b/lb, not provided, drug response, …) | 602,007 |
| ClinVar, terms defined by ClinVar-GKM | 537,574 |
| ClinGen/CGC/VICC Guidelines for Oncogenicity, 2022 | 9,767 |
| AMP/ASCO/CAP (AAC) Guidelines, 2017 | 9,287 |
| ClinGen Low Penetrance and Risk Allele Recommendations, 2024 | 2,240 |
| SVC v4 | 807 |

The ClinVar-defined codes are `conflicting classifications of pathogenicity` (528,112), `no classifications from
unflagged records` (8,730), `conflicting classifications of oncogenicity` (6) and 20 combination codes (726).

SCV codes are unchanged, so one code differs in case: an SCV classified `Pathogenic/Likely pathogenic` keeps the
upstream code `pathogenic/Likely pathogenic`, while the aggregate code is `pathogenic/likely pathogenic`. Compare
codes case-insensitively (see Known Issues).

### Fixes

- **Aggregate `strength` now matches the SCVs' (#226).** The old label-prefix rule gave Tier II–IV somatic
  statements `Strong` and left Likely oncogenic, low-penetrance and risk-allele aggregates without a strength.
  6,020 of 21,309,008 VCV and RCV records change (2,714 VCV, 3,306 RCV): Tier II `Strong` → `Potential` (2,001);
  Tier III and IV `Strong` → none (634); `Likely oncogenic` → `Likely` (2,630); `Pathogenic, low penetrance` and
  `Established risk allele` → `Definitive` (218); `Likely pathogenic, low penetrance` and `Likely risk allele` →
  `Likely` (537).
- **Aggregate `direction` now matches the SCVs' (#227).** The old rule gave `supports` to every label it didn't
  name. 4,779 records change (1,761 VCV, 3,018 RCV), all from `supports`: Tier III → `neutral` (447), Tier IV →
  `disputes` (187); VUS-high/mid/low and Uncertain risk allele → `neutral` (717); `conflicting data from
  submitters` → `neutral` (384); `association not found` → `disputes` (16); combinations of neutral terms →
  `neutral` (478); the FLAG label `no classifications from unflagged records` → `neutral` (2,550).
- **The pipeline can't write a record that 1.2.0 rejects** (#218). No current record is affected.
- **The bundle schema `$id` now resolves**:
  `https://w3id.org/clingen/schema/clinvar-gkm/1.2.0/clinvar-gkm-bundle.schema.json`.

### A new data line: `v1/1.2/`, and `v1/1.1/` is frozen

- **`v1/1.2/`** starts with one checkpoint monthly, `clinvar-gkm_2026-11.json.gz`, built from the 2026-10-31
  release with the 1.2.0 pipeline, and adds weekly deltas from 2026-11-08 on. Earlier releases are not rebuilt as
  1.2.0.
- **`v1/1.1/` is frozen**, kept indefinitely and unchanged: its monthlies (2026-07 … 2026-11), `00-latest`,
  archive and deltas, with a `MANIFEST.json`. Its weekly fulls and its Parquet set are removed. There are no 1.1
  weekly releases for November; 2026-11-08 and later are 1.2 deltas only.
- The root `index.json` names `v1/1.2` as current.

### Parquet: tables built by `gkm-bundle-parquet` 2.0

The Parquet set at `v1/1.2/parquet/` is built from each release's bundle by
[`gkm-bundle-parquet`](https://github.com/clingen-data-model/gkm-bundle-parquet) 2.0.0 and replaces the 22 tables
exported from BigQuery for the 1.1 line. **The JSON bundles are unaffected.** 20 tables (all evidence lines in
`evidenceLine`); no `data` column, every property in its own typed column, named as in the bundle (camelCase);
bare-id references with `_section` columns; qualifiers as STRUCTs; 4.6 GB instead of 13.2 GB. The tables rebuild
to the bundle's records exactly (`gkm-bundle-parquet rebuild`), and each set ships a `table-spec.json`. Queries
written for the 1.1 tables need rewriting.

### Documentation

The docs site is versioned (#228): one version per release line, chosen from a selector in the header; the root
opens the latest release, and `dev` shows unreleased changes from `main`. The Parquet pages describe the 2.0
tables, with a migration guide and a page on building your own tables and mini-bundles.

### What you need to do

**If you use the bundles:**

- Change `v1/1.1/` to `v1/1.2/` in download scripts, or read the current line from
  `https://data.clinvar-gkm.org/index.json`.
- Start from the checkpoint `v1/1.2/clinvar-gkm_2026-11.json.gz` and apply the 1.2 deltas from 2026-11-08. Don't
  apply a 1.2 delta to a 1.1 file: every VCV and RCV record changes in 1.2.0.
- Validate a bundle against the version it declares (`schema_version`): 1.2.0 bundles against the 1.2.0 schemas,
  1.1.0 bundles against 1.1.0.
- Code that reads bundles needs no change. If you read VCV/RCV `strength` or `direction`, expect the fixed
  values above.

**If you use Parquet:**

- Download from `v1/1.2/parquet/`. The 1.1 tables are gone.
- Rewrite queries for the 2.0 tables:
  Moving from the 1.1 Tables (`<DOCS 1.2>/parquet/migrating-from-1.1/`) maps every table and column and rewrites
  nine common queries.
- For an earlier release, build the tables from its bundle:
  Build Your Own Tables and Mini-Bundles (`<DOCS 1.2>/parquet/build-your-own/`).

## (b) Advance notice

**Subject:** ClinVar-GKM 1.2.0 on `<CUTOVER DATE>`: new download path `v1/1.2/`, new Parquet tables

**Body:**

On **`<CUTOVER DATE>`** we will publish ClinVar-GKM **1.2.0**. It changes where the files are and, for Parquet
users, what the tables look like. This note says what changes and what to do before then.

**What changes**

- **A new data line, `v1/1.2/`.** Download URLs change from `https://data.clinvar-gkm.org/v1/1.1/…` to
  `…/v1/1.2/…`. The new line starts with one checkpoint monthly, `clinvar-gkm_2026-11.json.gz`, built from the
  2026-10-31 release with the 1.2.0 pipeline, then adds weekly deltas from 2026-11-08 on.
- **`v1/1.1/` is frozen.** Its monthlies (through 2026-11), `00-latest`, archive and deltas stay, unchanged and
  indefinitely. Its **weekly fulls and its Parquet set are deleted**. There will be no 1.1 weekly releases for
  November. You may already have received the automatic announcement of the 2026-11 monthly for the 1.1 line:
  it is the last 1.1 monthly.
- **Schema 1.2.0.** The ClinVar profiles now allow exactly what the pipeline writes. Every published record
  already meets them. Every VCV and RCV classification gains a `primaryCoding`, and the aggregate `strength` and
  `direction` are fixed for some somatic, oncogenicity, VUS, risk-allele and flagged statements (about 6,000 and
  4,800 of 21.3 million VCV and RCV records). Every VCV and RCV record is rewritten.
- **New Parquet tables.** From 1.2.0 the Parquet set at `v1/1.2/parquet/` is built from the bundle by
  `gkm-bundle-parquet` 2.0.0: 20 tables instead of 22, no `data` column, camelCase typed columns, bare-id
  references. **The JSON bundles are unaffected by this.** Queries written for the 1.1 tables need rewriting.

**What you need to do**

*If you use the bundles:*

- Before `<CUTOVER DATE>`, download any **1.1 weekly full** you need; they are deleted. Monthlies and deltas
  stay.
- On `<CUTOVER DATE>`, point download scripts at `v1/1.2/` (or read the current line from
  `https://data.clinvar-gkm.org/index.json`), start from the 1.2 checkpoint monthly and follow the 1.2 deltas.
  Don't apply a 1.2 delta to a 1.1 file.
- Validate 1.2.0 bundles against the 1.2.0 schemas.

*If you use Parquet:*

- Before `<CUTOVER DATE>`, download the **1.1 tables** (`v1/1.1/parquet/`) if you want to keep them; they are
  deleted when the 1.2 set is published. They are not rebuilt.
- Read the migration guide now and plan your query rewrites:
  `https://dataexchange.clinicalgenome.org/clinvar-gkm/dev/parquet/migrating-from-1.1/` (the `dev` docs; the page
  moves to the released docs on `<CUTOVER DATE>`).
- To try the new tables before then, build them from any bundle with `gkm-bundle-parquet` 2.0.0 (on PyPI):
  `https://dataexchange.clinicalgenome.org/clinvar-gkm/dev/parquet/build-your-own/`.

Mirrors and caches: pause any job that mirrors `v1/1.1/weekly/` or `v1/1.1/parquet/` before `<CUTOVER DATE>`.

Questions or concerns: reply to this message, or post in GitHub Discussions, before `<CUTOVER DATE>`.
