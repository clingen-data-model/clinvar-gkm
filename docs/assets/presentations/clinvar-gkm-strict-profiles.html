This deck is for people who use ClinVar-GKM data: the JSON bundles and the Parquet tables built from them. Two ideas run through it. Open specs, strict profiles

The GKM Model: Four Specifications

Variation

VRS

Computable, digest-identified variants: Allele, SequenceLocation, CopyNumberCount, CopyNumberChange.

Categorical variation

Cat-VRS

Sets of variants defined by constraints, packaged as recipes such as CanonicalAllele and CategoricalCnv.

Variant annotation

VA-Spec

Statements that classify a proposition, with strength, direction, evidence lines and contributions.

Shared building blocks

gkm-core

Entity, Element, MappableConcept, ConceptSet, Coding and Extension, used by the other three.

A ClinVar-GKM bundle holds records from all four, in 20 typed sections. Each section is typed by a ClinVar profile of one of these classes.

ClinVar-GKM 1.2 · Strict profiles, fast tables

The GA4GH Genomic Knowledge Standards workstream curates these four specifications together as the GKM schema set. VRS identifies variants exactly. Cat-VRS describes categories of variants, such as "this allele on any assembly or transcript". VA-Spec carries the knowledge: a statement that classifies a proposition. gkm-core holds the shared pieces. Every record in a ClinVar-GKM bundle is an instance of one of these classes, narrowed by a ClinVar profile.

This is intentional in the GA4GH specs. They must serve labs, knowledge bases, registries and tools with very different data. So the base classes require little, accept free text where a community has not agreed on terms, and let you inline an object or point to it. For a consumer, that means many possible shapes for the same idea. The next slides show how profiles remove those options.

Three Layers, Each One Only Restricts

Base classes

What can be said

gkm-core Entity and MappableConcept · VRS Allele · Cat-VRS CategoricalVariant · VA-Spec Statement and Proposition

Standard profiles

How a community agrees to say it

VA-Spec VariantPathogenicityProposition and the ACMG 2015 statement profile · Cat-VRS CanonicalAllele and CategoricalCnv recipes

Implementation profiles

What one producer actually says

ClinVar-GKM 1.2: ClinvarScvStatement, ClinvarVariantPathogenicityProposition, ClinvarCanonicalAllele, …

A record that is valid against a ClinVar profile is still valid against its GA4GH class. Narrowing removes options; it never changes what a field means.

ClinVar-GKM 1.2 · Strict profiles, fast tables

Think of it as a funnel. The base classes define what can be said at all. Standard profiles, propositions and recipes are community agreements: for example, a pathogenicity proposition always uses the predicate isCausalFor, and a canonical allele always has exactly one defining allele constraint. Implementation profiles are the last step: one producer describes exactly what its data contains. Because every layer only restricts the one above it, ClinVar-GKM records stay valid GA4GH records.

A ClinVar profile is written as allOf: the GA4GH class, plus a block of restrictions. This is an abridged copy of the real source in schema/clinvar-gkm/clinvar-proposition-source.yaml. Here is one real chain. Each step only adds restrictions. The base Entity makes everything optional. VA-Spec’s Proposition is abstract with a free predicate. SubjectVariantProposition says the subject is a variant, and GeneticContextVariantProposition (not shown) adds gene context. The standard VariantPathogenicityProposition fixes the predicate to isCausalFor. ClinVar’s profile then says exactly how ClinVar writes it: an id is always present, the subject and object are pointers to records elsewhere in the bundle, and name, description, aliases, extensions and allele origin qualifier never appear.

gkm-core

Entity

Base of everything: optional id, name, description, aliases and extensions.

Cat-VRS

CategoricalVariant

Any set of variants, described by any list of constraints and members.

Recipe

CanonicalAllele

Exactly one DefiningAlleleConstraint, with liftover_to and transcribed_to relations.

ClinVar-GKM

ClinvarCanonicalAllele

ClinVar-GKM 1.2 · Strict profiles, fast tables

The same pattern on the variant side. Cat-VRS’s CategoricalVariant is fully open. The CanonicalAllele recipe is the community agreement: exactly one defining allele constraint, related to other forms by liftover and transcription. ClinVar’s profile requires constraints and members, makes the defining allele and every member a pointer to the allele section, and types ClinVar’s extensions: the HGVS list, the gene list, the variation type and so on. Copy number variants follow the CategoricalCnv recipe. Variants that fit no recipe, such as haplotypes and genotypes, use the plain CategoricalVariant with no constraints.

What ClinVar-GKM materializes

ACMG 2015: Where ClinVar-GKM Stands

In 1.2

A standard proposition in a ClinVar statement

  • Germline pathogenicity SCVs carry the standard VariantPathogenicityProposition: predicate isCausalFor, a variant subject, a condition object.
  • The statement is a ClinvarScvStatement, a profile of the base VA-Spec Statement. One statement class covers every ClinVar classification type.
  • ClinVar’s classification terms are kept as ClinVar codings.

Planned

The ACMG 2015 statement profile

  • Applied only to SCVs whose assertion method is ACMG 2015.
  • Locks classification to the five ACMG terms, strength to definitive or likely, and requires specifiedBy.
  • Open questions: mapping ClinVar’s free-text assertion methods, and matching ClinVar’s codings to the profile’s value sets.

ClinVar-GKM 1.2 · Strict profiles, fast tables

It is worth being precise here. In 1.2, a germline pathogenicity SCV uses the standard VA-Spec pathogenicity proposition, but the statement around it is ClinVar’s own profile of the base Statement, not the ACMG 2015 VariantPathogenicityStatement profile. That is because one ClinVar statement class has to cover every classification type ClinVar has, and because ClinVar records the assertion method as free text. Adopting the ACMG 2015 profile, and the AMP/ASCO/CAP 2017 profile for somatic statements, is planned as a later phase: only for SCVs whose assertion method says the guideline was used.

VA-Spec has standard propositions for pathogenicity, oncogenicity and the somatic clinical significance family. ClinVar also accepts older and broader classification types that no GA4GH profile covers yet. Rather than force them into a standard type, ClinVar-GKM defines one custom proposition per type. Each is a profile of VA-Spec’s SubjectVariantProposition, through a shared ClinvarGermlineCustomProposition, with a const type and a fixed predicate, so every one is still a valid VA-Spec proposition. The last row is a fallback for a classification that maps to no type; the current data has none, but the pipeline could write one. In Parquet these all land in one table, propositionClinvarCustom.

ClinVar-GKM 1.2 · Strict profiles, fast tables

Statements and evidence lines need the same treatment. The SCV statement is ClinVar’s profile of the base Statement. VCV and RCV records are aggregates: ClinVar’s own roll-up of many submissions, in classification and priority layers. VA-Spec has no standard for that yet, so ClinvarAggregateStatement and its evidence line define it. Somatic clinical impact submissions reuse the standard therapeutic, diagnostic and prognostic propositions inside a ClinVar evidence line. Each of these is a candidate for a future community profile; until then, the ClinVar profile says exactly what ClinVar means.

This is the principle behind the Parquet. The bundle is the public record; Parquet is a convenience view of it. Every value in a table must trace back to the JSON, and if a fact is needed that the bundle lacks, it goes into the bundle first. From 1.2, the tables are built only by the separate gkm-bundle-parquet tool, from the bundle you could download yourself. The old BigQuery export was retired because it re-derived the tables and drifted from the bundle. Because the projection is lossless, the tool can rebuild the bundle from the tables, and that round trip is checked before each publish.

The default column set is not hand-written. The tool reads the bundle schema and applies a fixed policy, so the producer publishes no column list. Every property the schema allows becomes a column, so the default set holds the entire bundle. Nested objects stay as structs rather than being flattened, which keeps the round trip exact. Pointers are the key move: a string that must match a section pattern becomes a foreign key you can join on. Anything the schema cannot type is kept as compact JSON text, and the tool lists every such position.

How narrowing reaches the tables

  • A forbidden property gets no column.
  • A pointer pattern becomes a foreign key.
  • A closed extension gets a typed value slot.
  • A required id drops the id_present column.

Columns stay nullable: required does not make a column NOT NULL.

ClinVar-GKM 1.2 · Strict profiles, fast tables

This is where the narrowing pays off for Parquet users. Run the same generator over the same records with the old and the new schema. With the open 1.1.0 schema you get 339 top-level columns, many of them always empty, 181 positions that fall back to JSON text, and no declared foreign keys. With the narrowed 1.2.0 schema you get 146 columns, 51 JSON-text positions, mostly extensions nested in extensions, and 26 foreign keys. One honest caveat: required fields do not make columns non-nullable; their only table effect is to drop the id_present flag.

This is the case for making narrowing the norm for every GKM producer, not just ClinVar-GKM. Before 1.2, the SCV class allowed about 49 thousand positions; ClinVar writes 119 of them. ClinVar-GKM 1.2 · Strict profiles, fast tables

This is the method ClinVar-GKM used in 1.2.0, offered as a recommended practice for any GKM implementation. Start from evidence: what your full release actually writes. Prune the rest, but do not forbid anything your pipeline could still produce, or a valid future record will fail. Require only what the data and the code both guarantee. Lock fixed values, make pointers name their target sections, and close every profile. Then harden the pipeline so it cannot break the profile, and validate every release. The profile becomes the producer’s contract, and the Parquet generated from it shows consumers only what is really there.

A Query, End to End

BASE="https://data.clinvar-gkm.org/v1/1.2/parquet"
curl -fO "${BASE}/scv.parquet"
curl -fO "${BASE}/propositionPathogenicity.parquet"

SELECT s.id, s.classification.name AS classification,
       p.predicate, p.object
FROM 'scv.parquet' s
JOIN 'propositionPathogenicity.parquet' p
  ON s.proposition = p.id
WHERE s.classification.name = 'Pathogenic'
  AND p.object = 'clinvar.trait:9580'
LIMIT 10;

s.proposition is a foreign key: the bare id from the bundle’s pointer.

proposition_section says which of the four proposition tables it points to.

classification is a STRUCT; read its fields with a dot.

p.object is the condition’s bare id.

ClinVar-GKM 1.2 · Strict profiles, fast tables

A typical query: pathogenic SCVs for one condition. Download two tables from the 1.2 Parquet folder and join them in DuckDB. The join key exists because the schema declares the SCV’s proposition as a pointer into the proposition sections; the tool turns that into a plain id column, plus a proposition_section column, because an SCV can point at any of four proposition tables. That _section column is the most common trap in joins, so check it whenever a pointer can target more than one table. The docs’ Joining Tables page walks through all five seams.

ClinVar-GKM 1.2 · Strict profiles, fast tables

Here is where the slicing story stands today. The first two rows are in the docs, with real outputs. The gene-panel and pathogenicity-only cuts use the same select options and should work, but nobody has run and documented them yet. The last three are planned: a plain filter that follows no pointers, a round trip for filtered builds, and a variant-sorted table so per-variant lookups over the CDN stop hitting rate limits. ClinVar-GKM does not publish curated subsets; the tool lets you cut your own.

Takeaways

Open specs make it possible to say anything. Strict profiles make it possible to rely on what was said.

Read the ClinVar profile, not just the GA4GH class. It lists exactly what you will get.

Start from the default Parquet set. Join on the foreign keys and check the _section columns.

Cut down with SQL slices or mini-bundles. Every value still traces to the published bundle.

ClinVar-GKM 1.2 · Strict profiles, fast tables

To sum up. The GA4GH specs are open so that many producers can use them. ClinVar-GKM is one producer saying exactly what its data contains, as strict profiles of those classes, with its own profiles where no standard exists yet. For you, that means a bundle you can code against without guessing, and Parquet tables that come straight from it: start with the whole set, then cut it down to your use.
