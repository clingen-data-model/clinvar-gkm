ClinVar-GKM parquet — join seams

The five places tables join. Three of them dispatch on an id prefix or a type column and silently drop rows if you join only one branch. Figures are from the 2026-10-18 release.

  2. ▸B · Proposition → Condition
  3. ▸C · Proposition → Statements
  4. ▸D · Aggregate nesting
  5. ▸E · SCV → aggregate
Seam A · Variant → Proposition

The clean one. All four proposition tables resolve to variation.id at 100 % — 28,077,355 references, zero unresolved. They share one column schema (from 1.1.0), so one glob, read_parquet('proposition*.parquet'), reads them all through subject_variant_id.

Query — one variant, every proposition (one glob reads all four tables) 
-- the 4 proposition tables share one schema; read them as one table
SELECT v.id, v.name, p.type, p.predicate
FROM 'variation.parquet' v
JOIN read_parquet('proposition*.parquet') p ON p.subject_variant_id = v.id
WHERE v.id = 'clinvar:51592';

Seam B · Proposition → Condition or ConditionSet

Every proposition table's object_id is polymorphic, deterministic, and complete: object_type names its table. Condition objects split three ways by prefix, and all three resolve; two land in conditionSet — one accessioned, one minted — so read the prefix to know which kind of set you have, but join both to the same table. The 13 therapeutic-response propositions point at a therapy or therapyGroup instead, with the tumor type in condition_qualifier_id.

Query — dispatch object_id on object_type, resolved to condition / conditionSet names 
-- resolve the object to a name: condition.name, or the set's members joined by ';'
WITH set_names AS (
    SELECT cs.id, string_agg(c.name, '; ') AS member_names
    FROM 'conditionSet.parquet' cs, unnest(cs.concepts) AS t(cid)
    LEFT JOIN 'condition.parquet' c ON c.id = cid
    GROUP BY cs.id
)
SELECT DISTINCT p.object_id, p.object_type,
    coalesce(c.name, sn.member_names, 'UNRESOLVED') AS condition_name
FROM 'propositionPathogenicity.parquet' p
LEFT JOIN 'condition.parquet' c  ON p.object_type = 'condition'    AND c.id  = p.object_id
LEFT JOIN set_names           sn ON p.object_type = 'conditionSet' AND sn.id = p.object_id
WHERE p.object_id IN (
    'clinvar.trait:16789', 'clinvar.traitset:10013',
    'clinvar.conditionset:vcv-c620785e2025efde81bdd15c814fa83d')
ORDER BY p.object_type;

Seam C · Proposition → Statements · 1:1

proposition_id is unique within each statement table and across all three combined — 28,075,787 references, 28,075,787 distinct. A proposition has at most one statement, so it is effectively a side-table of its statement. Only the 1,568 evidence-line targets in propositionSomaticClinicalImpact (diagnostic, prognostic, therapeutic response) have no statement.

Query — SCVs across proposition tables: scv + classification + proposition type + variant & condition names 
-- read all four proposition tables keeping subject + object, then resolve both to names.
-- (a statement's object is always a condition or set; therapy objects belong only to the
--  therapeutic-response propositions, which no statement classifies.)
WITH prop AS (
    SELECT id, type, subject_variant_id AS variant_id, object_id
      FROM read_parquet('proposition*.parquet')
),
set_names AS (
    SELECT cs.id, string_agg(c.name, '; ') AS member_names
    FROM 'conditionSet.parquet' cs, unnest(cs.concepts) AS t(cid)
    LEFT JOIN 'condition.parquet' c ON c.id = cid GROUP BY cs.id
)
SELECT s.id AS scv_id, s.classification.name AS classification, p.type AS proposition_type,
       p.variant_id, v.name AS variant_name,
       p.object_id, coalesce(c.name, sn.member_names) AS object_name
FROM 'scv.parquet' s
JOIN prop p ON p.id = s.proposition_id
LEFT JOIN 'variation.parquet' v  ON v.id  = p.variant_id
LEFT JOIN 'condition.parquet' c  ON c.id  = p.object_id
LEFT JOIN set_names           sn ON sn.id = p.object_id
WHERE s.id IN ('clinvar.submission:SCV000056982.2',
               'clinvar.submission:SCV007129927.1',
               'clinvar.submission:SCV002796738.1')
ORDER BY proposition_type;

Seam D · Aggregate nesting — a 2-level forest, SCVs always at the leaves

A root statement carries the overall classification and cites no SCVs directly; its child statements partition the submissions by evidence subgroup and cite the SCVs. Every aggregate child has exactly one parent, and no edge crosses an accession.

Query — one aggregate group: root cites children, children cite SCVs 
-- unnest has_evidence_lines → evidence_items for one accession
SELECT s.id AS statement, count(*) AS cites
FROM (SELECT id, unnest(has_evidence_lines) el_id
      FROM 'vcv.parquet' WHERE id LIKE 'VCV000012871.%') s
JOIN (SELECT id, unnest(evidence_items) item
      FROM 'vcv_evidenceLine.parquet') el ON el.id = s.el_id
GROUP BY 1 ORDER BY 1;

Seam E · every SCV to its RCV and VCV group, in one pass

Because no aggregate edge ever crosses an accession, the accession in the citing statement's own id already names the group — so one pass over has_evidence_lines ⋈ evidence_items yields every SCV↔accession pair. No recursion, no self-join on the edges.

Query — every SCV → its VCV accession in one pass (swap vcv/rcv for the other tier) 
-- the accession in the citing statement id names the group; no recursion needed
SELECT regexp_extract(e.parent, '^VCV[0-9]+', 0) AS vcv_accession, e.child AS scv_id
FROM (
    SELECT s.id AS parent, it.item AS child
    FROM (SELECT id, unnest(has_evidence_lines) AS el_id FROM 'vcv.parquet') s
    JOIN (SELECT id, unnest(evidence_items)     AS item  FROM 'vcv_evidenceLine.parquet') it
         ON it.id = s.el_id
) e
WHERE e.child LIKE 'clinvar.submission:%';
