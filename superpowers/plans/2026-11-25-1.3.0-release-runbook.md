# 1.3.0 release runbook

**Goal:** publish ClinVar-GKM 1.3.0 (SCV statement profiles, ADR 0015; corrected guideline codings; VUS-high/mid/low
strengths) as the new line `v1/1.3/`, and freeze `v1/1.2/`.

**Model:** the [1.2.0 runbook](2026-11-18-1.2.0-release-runbook.md). Its commands are reused below; differences are
called out. **[OK]** marks a step that needs the user's go-ahead (live R2, BigQuery spend, shared tables, merges
into `1.0`, tags, email).

## Decisions

| # | Decision | Proposed |
| --- | --- | --- |
| R1 | Scope (**decided 2026-11-25**) | 1.3.0 = #304 (VUS strengths) + #305 (SCV profiles) + the build gates **and** what was planned for 1.4.0: P1 (release and line in every bundle root), P4 (change events in the delta bundle, for a `changes` Parquet table) and P5 (version and date fields on VCV and RCV records). P1/P4/P5 need their own spec and plan (in progress); their build steps join steps 5–6 below, and the cut-over date follows from when they are ready (see "If ClinVar posts 2026-12 after 2026-12-06" for a later checkpoint). |
| R2 | Checkpoint (**decided 2026-11-25**) | `v1/1.3/` starts at monthly **2026-12 ← 2026-11-29**, the ADR 0002 source of ClinVar 2026-12 (if ClinVar posts ClinVarVCVRelease_2026-12 before the 12-06 release). One full rebuild. First 1.3 delta: 2026-12-06, baseline 2026-11-29. |
| R3 | Old line (**decided 2026-11-25**) | 2026-11-29 is the last 1.2 weekly; `v1/1.2/` gets a final monthly 2026-12 (a copy of the 11-29 weekly, as D2 in 1.2.0), then is frozen. |
| R4 | Deferred 1.2.0 gates (**decided 2026-11-25**) | Run them this time: proposition conformance and expected difference (`release-validation.md` follow-ups). The 28 empty MedGen names stay a follow-up. |
| R5 | Older releases (**decided 2026-11-25**) | Published releases keep the old codings (ADR 0008: published files are immutable); 1.3 is not backfilled. Every correction follows from the old record, so the docs publish the old → new table and `recode-1-3-0.py`, which gives an older bundle 1.3.0's codings (Known Issues, `#guideline-codings-before-1-3-0`). |

## Invariants

- **The shared lookup changes once, after the last 1.2 build.** `clinvar_ingest.clinvar_clinsig_types` is read
  live by the procs of both lines. Apply it only after the 2026-11-29 1.2 weekly is published.
- **1.2 weeklies run from `1.0` only.** `main`'s `run-release.sh` stops at `check-clinsig-lookup.sh` until the lookup
  is applied, and its procs write 1.3.0 records.
- **1.3.0 is built in full**, and the first 1.3 delta's baseline must be a dataset rebuilt with the 1.3.0 procs.
  `check-scv-codings.sh --with-baseline` (run-release step 3) enforces both.
- Forward-merges are merge commits, never squashes (#243). A pushed tag never moves.

## Steps

### 0. Land the prerequisites **[OK: merges]**

- clinvar-ingest-bq-tools **#53**: lands #52 (the codings) on `main`; closes #50. `main` holds #51 only until then.
- clinvar-gkm: the build-gates PR (`check-clinsig-lookup.sh`, `check-scv-codings.sh`).
- Live negative check (about $0.01): `check-clinsig-lookup.sh` must fail on today's lookup, naming the
  `tier N`, `(AAC)`, `SVC v4` and `pathogenic/Likely pathogenic` rows; `check-scv-codings.sh 2026-11-22` must
  fail with "built before schema 1.3.0".

### 1. Release-prep PR into `main`

- `r2_layout.py:43-48`: add `"v1/1.3/": current`; `v1/1.2/` → `frozen`, schema `"1.2.0"`, `superseded_by
  "v1/1.3/"`; `CURRENT_LINE = "v1/1.3/"`. `r2-common.sh:19` and `run-release.sh:169`: default `R2_LINE` `v1/1.3/`.
  Update `test_r2_layout.py`.
- Parquet VM runner (outside the repo, `~/clinvar-gkm-release-1.2.0/parquet-vm/run-parquet-vm.sh:50`): copy it for
  1.3.0, with `EXPECT_TAG=1.3.0`.
- Gate: pytest, `bash -n` + `shellcheck`, strict docs build + link check.

### 2. Last 1.2 weekly: 2026-11-29 **[OK: BigQuery, live R2]**

The normal weekly, from a `1.0` worktree, old procs, old lookup: `run-release.sh 2026-11-29 --full-procs`, then
`oracle-delta-reconstruction.sh` and the Parquet VM run, as for 11-22.

### 3. Snapshot 2026-11-29 **[OK: BigQuery, ~$0]**

Before anything changes: table clones of the 11-29 `gkm_dict_*` tables and the `gkm_vcv_*` / `gkm_rcv_*` aggregate
tables into a scratch dataset (labelled, two-week expiry). They let a failure of the step 6 recode gate be traced to
its tables.

### 4. Apply the lookup **[OK: shared BigQuery table]**

From clinvar-ingest-bq-tools `main` (after #53), `00-setup-translation-tables.sql`:

- First diff every other table the script recreates (`clinvar_statement_categories`, `clinvar_statement_types`,
  `clinvar_proposition_types`, `scv_clinsig_map`, `submission_level`, `status_rules`, `status_definitions`)
  against the live tables (scratch copies built from the script, read-only compare). Expected: no differences.
- Clone the live table first (`clinvar_ingest.clinvar_clinsig_types_pre_1_3_0`).
- Run only the `clinvar_clinsig_types` `CREATE` + `INSERT` (the stage-only block is skipped in `clingen-dev`).
- Gate: `check-clinsig-lookup.sh` passes. The live table equals the script's rows (the Task 4.2 scratch build used
  the same rows: 0 old codes in every SCV, VCV and RCV coding).
- Rollback: restore the clone. Drop it after step 11.

### 5. Deploy the 1.3.0 procedures **[OK: BigQuery]**

The set is `git diff --name-only 1.2.0 origin/main -- src/procedures` (the SCV statement proc; the VCV/RCV comment
changes; the files whose version lines changed). `bq query --dry_run` each, deploy in dependency order, then compare
every deployed body with the file (`INFORMATION_SCHEMA.ROUTINES`, 1.1.0 runbook §1). Rollback: redeploy from tag
`1.2.0`.

### 6. Rebuild 2026-11-29 in full and gate it (no upload) **[OK: BigQuery, ~$2–3.5]**

From a `main` worktree (submodules initialised, `venv/3.12` with orjson):

```bash
src/scripts/run-release.sh 2026-11-29 --full-procs --start-step 2 --skip-parquet --bootstrap-monthly=2026-12 --dry-run
```

Step 2 runs `check-clinsig-lookup.sh`, re-stamps `gkm_pipeline_version` and runs every proc in full. Step 3 runs
`check-scv-codings.sh 2026-11-29` (must be all 0), then prints the bootstrap. It refuses until ClinVar has
posted ClinVarVCVRelease_2026-12 and 11-29 is its source; that is expected before step 8. Then the gates:

| Gate | Command / check | Pass |
| --- | --- | --- |
| Codings (build) | `check-scv-codings.sh 2026-11-29` | all 0 |
| Expected difference (recode gate) | download the published 1.2 weekly full of 2026-11-29; `docs/assets/scripts/recode-1-3-0.py` it; compare it with the staged 1.3 full record by record (same sections and keys, each record equal as JSON) | every record equal; only `schema_version` differs. Record how many records the script changed (about 2,000 SCVs plus the aggregates) for the 1.3.0 results. A difference is either a 1.3.0 change the script and Known Issues miss (fix both) or an unintended change (stop); the step-3 snapshot finds its tables |
| Strict validation | `release-gkm.sh 2026-11-29 <ver> --month-label=2026-12 --no-upload` (rs, every record) | 0 failures; `"schema_version": "1.3.0"` |
| Toolkit sample | `sample-bundle.py` 1% + `validate-bundle.sh --engine toolkit` | 0 failures |
| Proposition conformance | `validate-proposition-conformance.sh` on 2026-11-29 | 0 (deferred in 1.2.0) |
| Community profile counts | `community-profile-conformance.py <staged full> --write-docs docs/profiles/community-profiles.md` | reasons are only the documented differences; commit the counts in step 9 |
| Parquet | compile the staged full's `scv` table with gkm-bundle-parquet locally | `classification.primaryCoding.name` is present |

Rollback: rebuild 2026-11-29 with the `1.2.0` procs and the old lookup; nothing is published yet.

### 7. Advance notice **[OK: email + Discussion]**

By hand (ADR 0010). Content: what changes (codes `tier i`, `ACMG/AMP/CAP/ClinGen SVCv4.0`, lower-case combined code,
tier names on the coding, VUS strengths), the new `v1/1.3/` line starting at the 2026-12 checkpoint, `v1/1.2/`
frozen, and the dates of steps 8–11.

### 8. Cut the release (once ClinVarVCVRelease_2026-12 is posted, before the 2026-12-06 run)

1. **Final 1.2 monthly** **[OK: live R2, triggers the automated email]**. From `origin/1.0` (old code):
   `R2_LINE=v1/1.2/ src/scripts/upload-gkm-to-r2.sh 2026-11-29 <ver> - --month-label=2026-12 --from-weekly`
   (`--dry-run` first). It is a server-side copy of the published 11-29 weekly, so the rebuild does not affect
   it. Check `ops/announcements` `announced.json` so the 1.3 checkpoint is not announced twice.
2. **Release branch** **[OK: PR merge into `1.0`]**. `git switch -c release/1.3.0 origin/1.0 && git merge --no-ff
   origin/main`. In the PR: changelog `## Unreleased: 1.3.0` → `## 1.3.0 — <date>`, `CITATION.cff`, the 1.3.0
   results in `release-validation.md`. Gate: as in step 1, and `git diff origin/main release/1.3.0 -- src schema`
   is empty.
3. **Tag** **[OK]**. `git tag -a 1.3.0 origin/1.0`; `gh release create 1.3.0 --target 1.0` (notes = changelog
   section). Gate: `curl -sI https://w3id.org/clingen/schema/clinvar-gkm/1.3.0/clinvar-gkm-bundle.schema.json` → 200.
4. **Start `v1/1.3/`** **[OK: live R2]**. From the tag:
   `run-release.sh 2026-11-29 --start-step 3 --skip-parquet --bootstrap-monthly=2026-12` (`--dry-run` first).
   Gate: root `current` = `v1/1.3`; `v1/1.3/index.json` has monthly 2026-12, `source_release` 2026-11-29,
   `schema_version` 1.3.0.
5. **Freeze `v1/1.2/`** **[OK: live R2, deletes weekly/ and parquet/]**. `r2-freeze-line.sh v1/1.2/` (dry run),
   then `--apply`, once. Gate: `PASS: v1/1.2/ frozen`.

### 9. Parquet, docs, examples **[OK: VM, docs deploy]**

- Parquet: the 1.3.0 VM runner on the checkpoint (`release-gkm-parquet.sh` reads the monthly the index lists).
- Examples: regenerate `examples/` from the staged full; validate with the toolkit.
- Docs: point the asset URLs at the new line (`clinvar-gkm.org/1.2/assets/` → `/1.3/assets/`, 10 places);
  `known-issues.md` "Release status" → 1.3; the 1.3.0 results in `release-validation.md` (the recode gate's
  counts, the community counts); check the dates in `keep-current.md` "Line changes" (2026-12 ← 2026-11-29,
  first delta 2026-12-06).
- Docs: commit the community counts and examples to `1.0`; `docs-line-sources.txt` 1.3 → the `1.0` tip; dispatch
  `deploy-docs.yml` for 1.3 and 1.2.

### 10. Forward-merge `1.0` → `main` **[OK: merge commit]**

Gate: `git describe origin/main` = `1.3.0-N-…`, never exactly `1.3.0`.

### 11. First 1.3 weekly: 2026-12-06 **[OK: BigQuery, live R2]**

`run-release.sh 2026-12-06 --full-procs` from `1.0`. Step 3 checks 12-06 and its baseline 11-29 (both 1.3.0). Gate:
`oracle-delta-reconstruction.sh 2026-11-29 2026-12-06 <ver>` = 0,0,0 on every section. Then announce 1.3.0 (email and
Discussion) and close the release.

11-29 is then not the source of the 2026-12 monthly: 12-06 is. Build 12-06 as a 1.2 weekly first (step 2), then
do steps 3–6 on 12-06, and start `v1/1.3/` at 2026-12 ← 12-06. Change the dates in `keep-current.md` "Line changes"
to match.
