Strict-Mode Schema Validation (B1) Plan¶

For agentic workers: REQUIRED: Use superpowers:subagent-driven-development (if subagents available) or superpowers:executing-plans to implement this plan. Steps use checkbox (- [ ]) syntax for tracking.

Goal: Make validate-schema-conformance.py --no-relax pass on real published data, so strict validation can gate releases. Separate the generator/schema defects from genuine data defects. Only the data defects change published data, so only they bear on the consolidated rebuild and backfill.

Parent plan: B1 in 2026-10-16-parquet-followups.md. That plan assumed the fix belongs in gkm-metaschema. The investigation below shows a clinvar-gkm source fix is enough, needs no generator release, and was verified end to end.

Answer to the backfill question: the strict-mode failures are schema defects, not data defects, and fixing them changes no published data. Checking real data turned up one genuine data defect: malformed citation Documents on up to 3,872 SCVs in the 2026-10 full (Task 5). It fails default (relaxed) validation too, so it was never a strict-only problem. It went unnoticed because only deltas were validated, and none of the affected SCVs are in the 2026-10-11 delta. Fixing it changes published scv records, so it has to be decided before the rebuild.

Root cause 1: closed *Properties mixins inside allOf (all five sections)¶

Each ClinVar profile is composed as allOf: [<upstream base>, <ClinVar mixin>], with unevaluatedProperties: false on the outer class. The outer closure is correct. The problem is the mixin.

"ClinvarScvStatement": {
  "allOf": [
    { "$ref": "/ga4gh/schema/va-spec/1.1.0/json/Statement" },
    { "$ref": "#/$defs/ClinvarScvStatementProperties" }
  ],
  "unevaluatedProperties": false
},
"ClinvarScvStatementProperties": {
  "properties": { "proposition": …, "hasEvidenceLines": …, "extensions": … },
  "additionalProperties": false
}

additionalProperties only sees its own schema's properties. So the mixin rejects every property that the base Statement supplies: id, type, classification, and the rest. Every SCV/VCV/RCV statement fails on that branch. The variant and custom-proposition profiles fail the same way.

There are nine such mixins, all protectedClassOf $defs:

Mixin Schema
ClinvarScvStatementProperties ClinvarScvStatement
ClinvarAggregateStatementProperties ClinvarAggregateStatement (used by VCV and RCV)
ClinvarGermlineCustomPropositionProperties ClinvarGermlineCustomProposition
ClinvarSomaticEvidenceLineProperties ClinvarSomaticEvidenceLine
ClinvarCategoricalVariantProperties, ClinvarCanonicalAlleleProperties, ClinvarAlleleProperties, ClinvarSequenceLocationProperties, ClinvarSequenceReferenceProperties ClinvarCategoricalVariant

Why the generator emits false: the source YAML declares additionalProperties: true on 8 of the 9 mixins (ClinvarGermlineCustomPropositionProperties declares nothing). But gkm-metaschema source_proc.py (lines ~906–913) overwrites it unconditionally: every non-abstract class in a strict source gets additionalProperties: false, or unevaluatedProperties: false if it is composed. The authored true is silently discarded. The same code leaves abstract classes open on purpose. Its comment notes that even additionalProperties: true would be wrong on a mixin, because it marks every property as evaluated and so disables the outer unevaluatedProperties: false.

Minimal reproduction (pure JSON Schema 2020-12, no project schemas):

base  = {"$id": "urn:Base",  "type": "object", "additionalProperties": False,
         "properties": {"id": {"type": "string"}, "type": {"type": "string"}, "extensions": {"type": "array"}}}
mixin = {"$id": "urn:Mixin", "type": "object", "additionalProperties": False,      # <- the defect
         "properties": {"extensions": {"type": "array", "maxItems": 3}}}
profile = {"allOf": [{"$ref": "urn:Base"}, {"$ref": "urn:Mixin"}], "unevaluatedProperties": False}
# {"id": "x", "type": "Statement", "extensions": []}
#   -> "Additional properties are not allowed ('id', 'type' were unexpected)"
# Drop the mixin's additionalProperties: valid, and {"bogus": 1} is still rejected by the outer
# unevaluatedProperties.

Root cause 2: GeneListItem describes an older record shape (variation only)¶

With root cause 1 fixed, the statement and proposition sections pass, but 15,756 of 15,758 variants still fail. The reported error is misleading: ClinvarCategoricalVariant is a oneOf with unevaluatedProperties: false. When every branch fails, no property counts as evaluated, so the outer error lists every field. Testing one branch at a time narrows it to the clinvarGeneList extension.

Shape
Data, every gene-list item {"gene": "#/gene/ncbigene:242", "relationship_type": …, "source": …}
GeneListItem schema entrez_gene_id, hgnc_id, symbol, relationship_type, source, iris, plus additionalProperties: false. There is no gene.

The data is the intended form. Gene details moved to the gene section, and the docs already describe the #/gene/ pointer (output-reference/cat-vrs.md, id-references.md). The schema was never updated, and relaxed mode hid that by stripping additionalProperties. Across the 2026-10 monthly full, all 7,346,154 gene-list items have gene, relationship_type and source. None is missing one, and none has a gene that isn't a #/gene/ncbigene: pointer. This is a schema defect, not a data defect.

Latent limitation: a closed upstream parent can't be extended¶

If a mixin adds a property its upstream base doesn't declare, the closed base rejects it. Only one case exists: ClinvarCanonicalAlleleProperties.definingContext. cat-vrs CanonicalAllele (unevaluatedProperties: false) over CategoricalVariant (additionalProperties: false) has no definingContext. No record uses it (0 of 4,647,675 variants in 2026-10, and no procedure emits it), so it causes no failures today. It would fail strict validation the first time it was populated.

Prototype: corrected composition on real data¶

Neither gkm-metaschema nor any committed schema was changed. Two prototypes were run:

  • Programmatic transform: strip the closure from every allOf-branch target, and point composed references at open copies of the upstream bases.
  • Source fix (the recommendation): in a scratch copy of the four *-source.yaml files, mark the nine mixins abstract: true, remove their additionalProperties: true, and update GeneListItem. Then regenerate with the installed generator (make -C schema/clinvar-gkm) and validate with the unmodified validate-schema-conformance.py registry in strict mode (relax=False).

The two prototypes gave identical results. Opening only the mixins is enough: no upstream base has to be opened, because no record uses a property its base lacks (see the latent limitation above).

Bad DOI values in the full, from SELECT … FROM scv.parquet:

Field Values
specifiedBy.reportedIn.doi https ×3,746, doi.org/10.1002/humu.23630 ×52, then doi:10.…, https://doi.org/10.…, DOI: 10.…, a bare PMID (25741868), a PMC id (PMC8832287)
reportedIn[].doi doi:10.…, doi.org/10.…, https, doi/10.…, http://dx.doi.org/10.…, org/10.…, doi, values with a trailing .

The va-spec Document requires doi to match ^10.(\d+)(\.\d+)*/[\w\-\.]+ and urls[] to match ^(https?|s?ftp)://. The "https" DOI also produces the meaningless URL https://doi.org/https.

Origin: gkm-scv-statement-proc.sql Step 7b (temp_scv_citations, which feeds reportedIn) and Step 7c (temp_scv_method, which feeds specifiedBy.reportedIn) copy ClinVar's citation cid.id into doi verbatim. Their ELSE branch also puts cid.curie (7b) or source:id (7c) into urls, even when the value isn't a URL.

Recommendation: where the fix goes¶

Option Verdict
A. clinvar-gkm source YAML: mark the 9 mixins abstract: true and drop their additionalProperties: true; fix GeneListItem Recommended. Verified end to end with the installed generator. It uses the generator's own documented rule (abstract classes are left open, concrete ones closed), so no metaschema release is needed. It also matches how va-spec composes its own profiles.
B. gkm-metaschema generator: honor or reject an authored class-level additionalProperties, and leave protectedClassOf mixins open Worth doing upstream, but not blocking. File an issue: the silent overwrite of an authored true is a trap for every profile author.
C. clinvar-gkm post-processing step after make Rejected. It is a second, hidden schema source, and the published JSON would still differ from what the YAML says.
D. Validator-only (today's relax) Rejected as the fix. The published schemas are what consumers and the GA4GH gkm-toolkit validate against, so they must be correct as published.

Deterministic output (deferred): json.dump(..., sort_keys=False) at source_proc.py:482 lets $defs come out in set order. The scratch regeneration reordered $defs in three files (ClinvarAggregateStatement, ClinvarCategoricalVariant, ClinvarScvStatement) with no change in content. Switching to sort_keys=True belongs in gkm-metaschema and stays deferred. It would also reorder properties in every emitted file, so it should land as its own one-time-churn regeneration. Until then, follow the existing rule in scripts.md: revert files whose JSON is semantically unchanged, and keep only the real diff.

Task 5: Fix malformed SCV citation Documents (data, changes published scv)¶

File: src/procedures/gkm-scv-statement-proc.sql, Steps 7b and 7c.

  • [ ] Investigate (read-only BigQuery): find the raw ClinVar citation source/id/url behind the "https" DOIs (3,746 rows) and the PMID: URLs. Establish whether the bad value is in the ClinVar XML or comes from upstream clinvar-ingest parsing. If it is upstream, open an issue there as well.
  • [ ] DOI: set doi to REGEXP_EXTRACT(cid.id, r'(10\.\d+(?:\.\d+)*/[^\s]+?)\.?$'). That strips the https://doi.org/, doi.org/, dx.doi.org/, doi: and DOI: (with its trailing space) prefixes and a trailing period. It is NULL when no DOI is present (https, doi, a PMID or PMC id). Build the https://doi.org/%s URL only from the normalized DOI.
  • [ ] URLs: emit a urls entry only when it matches ^(https?|s?ftp)://. Route PubMed-style sources (PMID, and others that turn up in the investigation) to pmid and a PubMed URL, rather than through the ELSE curie branch.
  • [ ] Empty documents: if a citation Document ends up with no pmid, doi or urls, drop it. In 7c, set specifiedBy.reportedIn to NULL.
  • [ ] Determinism: keep both steps byte-identical between full and incremental runs. They are computed globally and LEFT-JOINed into gkm_dict_scv, so the carry-forward invariant isn't at risk.
  • [ ] Data impact: gkm_dict_scv is a per-SCV carry-forward output. An incremental run only recomputes changed SCVs, so the fix reaches the up-to-3,872 unchanged SCVs only if the SCV step runs in full mode once in the forward rebuild (the same pattern as A1's variant step). Expect the full-vs-incremental oracle to pass only after that full run, and the first delta afterwards to carry those SCVs as changes.

Task 5 needs a backfill decision before the forward rebuild, following the parent plan's rule.

  • Forward: requires the SCV step in full mode once. The first post-fix delta then carries the corrected SCVs, so reconstruction stays consistent without touching past releases.
  • Past fulls: they are non-conformant today, even under relaxed validation. Two options:
  • (a) Leave them and document it.
  • (b) Patch the affected scv records in the same JSON backfill pass that A1 already does on every monthly full. Recommended: the files are rewritten anyway, and the extra work is a few thousand records per full.
  • Parquet: re-exporting scv for every monthly set costs a lot more (about 3 GB per month). Leaving the past scv Parquet as it is would be reasonable; the JSON bundles are the conformance artifact.
