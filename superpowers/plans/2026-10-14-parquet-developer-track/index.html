Parquet Developer Track Implementation Plan¶

Status: implemented (2026-10-15), PR #139. The checkboxes below are ticked; where the build departed from a step, the difference is recorded here rather than by leaving the box open.

Renamed during review: "section" became "table" throughout the track. Each bundle section is exactly one Parquet table.

Planned As built
One Section at a Time · first-queries.md Anatomy of a Table · table-anatomy.md
The 22 Sections · section-map.md The 22 Tables · tables.md
Joining Sections · joining.md Joining Tables · joining.md
parquet-section-map.html parquet-table-map.html

Added beyond the plan: a live DuckDB-Wasm console on Start Here (vendored runtime); a third diagram, parquet-vcv-levels.html (reading a variant's statements); a complete per-table column reference on The 22 Tables; diagram table boxes linked to that reference; a pinned header with a scroll-tracking mini list of the diagrams in each frame; the "Materialize the joins you repeat" section on Working at Scale; R in Beyond DuckDB.

Departures from the steps as written:

  • Remote querying (Conventions): SET threads=1 + http_retries no longer gets a big-table scan through. The CDN returns HTTP 429 after ~55 requests in ~10 s, even single-threaded. The pages teach "explore remotely (footer, LIMIT, small tables), download to analyze", and drop the throttle as a workaround.
  • Task 4, step 5: the classification.name leaf is well under 1 MB on disk, not ~140 MB. The page uses the measured figure, and also teaches grouping by the normalized classification.primaryCoding.code (44 submitted spellings → 34 code–guideline pairs).
  • Task 8, step 2 (row-group targeting): the published files are not sorted by any lookup key, so a filter can't skip row groups. The page explains that, and points to materialized, sorted tables as the way to get row-group pruning.
  • Task 11: besides the pointer, data-access/parquet.md got two corrections: not every table has id/data, and two listed varcustom columns don't exist.
  • Also found: the repo .gitignore's bare parquet/ rule hid docs/parquet/; !docs/parquet/ added.

For agentic workers: REQUIRED: Use superpowers:subagent-driven-development (if subagents available) or superpowers:executing-plans to implement this plan. Steps use checkbox (- [ ]) syntax for tracking. Use the repo's write-docs skill for every page created or edited here.

Goal: Add a Parquet-focused developer track that teaches someone to go from "never opened a Parquet file" to "joining across 22 sections confidently" — a learning path, not a file list. Each page opens with something runnable before any prose about the model.

Problem being solved: The JSON/bundle consumer has three whole nav tabs — Data Guide (output format, per-statement-type pages, ID references, examples), Data Model (33 class pages), Pipeline (how it is built). The Parquet consumer has one page, data-access/parquet.md, which sits under Downloads and is organised around distribution mechanics. It does five jobs at once (release browsers, the 22-file table, prerequisites, query examples, delta reconstruction) and never states the relational model: which columns are keys, which joins are polymorphic, which ones silently drop rows. Today a Parquet consumer has to reverse-engineer that. Three of the five join seams cannot be guessed from column names.

The asymmetry in one line: JSON consumers are taught a pointer model (#/condition/clinvar.trait:17556); Parquet consumers need a relational model (tables, keys, prefix-dispatched foreign keys). They are different mental models, so a Parquet reader cannot simply be redirected to the Data Guide.

Architecture: A new top-level nav tab Query the Data, sibling to Data Guide, with seven pages ordered by difficulty. data-access/parquet.md stays exactly where it is and keeps all its anchors — it becomes the distribution page (release browsers, file table, stable URLs, deltas) and gains a pointer into the new track. Two new self-contained HTML diagrams live in docs/assets/diagrams/ and are embedded with <iframe>, following the bundle-section-map.html precedent.

Tech Stack: Zensical (Material theme, zensical build --strict), Markdown with pymdownx.details collapsible call-outs and admonition, hand-authored inline-SVG diagrams in standalone HTML (no JS libraries, CSP-safe), DuckDB CLI as the teaching tool.

Branch: docs/parquet-developer-track off main. Verifies with zensical build --strict and zensical serve.

Conventions:

  • No SQL ships unrun. Every query in these pages must be executed against a real downloaded monthly set and its output pasted from the actual run. Counts are release-dependent, so each page states its release date once and uses figures from that release only.
  • Zensical --strict builds and validates every .md regardless of nav, and these pages cross-link each other — so a build passes only once all seven exist. Create them all, then build and commit together (the same ordering constraint the Downloads redesign hit; see its plan, Chunk 3).
  • Preserve existing heading text in data-access/parquet.md — Parquet Files, Download, Query, Column Reference, Applying Deltas (keeping a Parquet set current) — at least ten inbound links and two prior planning docs reference them.
  • Terminology per .claude/rules/docs.md: GKM = the schema set, GKS = the workstream; say bundle, not dictionary; Variant/Variation in headers.
  • Remote querying is taught — within a boundary. data.clinvar-gkm.org/v1 serves HTTP range requests with CORS open, so DuckDB (httpfs autoloads) queries https://.../00-latest/<section>.parquet directly. Use it as the default for light work (Start Here, single-table, targeted / LIMIT reads); it is zero-friction and ~0.5 s. For heavy work (joins, full scans on big sections) download once and query local files — a parallel full-column scan over a big file bursts range requests and trips Cloudflare's rate limiter (HTTP 429). Teach that boundary and the SET threads=1 + http_retries throttle as the reason, not a footnote. Never teach pointing a query at the old pub-*.r2.dev host.

Chunk 0: Source material — what is already verified¶

No task here; this is the input inventory so implementers do not re-derive it.

A full structural audit of the 14 Oct 2026 release was completed: 22 tables, 90,209,827 rows, 26 foreign-key edges, 166,889,379 references, all resolving. The findings that the track must teach:

Fact Why a reader needs it
Four polymorphic FKs dispatch on id prefix object_condition_id, proposition_id, variation.members[], evidence_items[]. Joining one branch silently drops the rest.
variation.members[] reads as a broken FK (98 %) until split by VRS prefix VA.→allele, CN.→copyNumberCount, CX.→copyNumberChange, each 100 %.
proposition_id is 1:1, not 1:N Unique within each statement table and across all three combined. A proposition is a side-table of its statement.
gene_context_name joins gene.name, which is not unique And is NULL on ~76 % of rows. Two reliable gene-id edges exist instead.
SCVs are always leaves in evidence-line branching Measured: zero SCV ids ever appear as the parent of an evidence edge.
Aggregate tiers are forests, depth ≤ 2, and no edge crosses an accession Which is why the SCV↔aggregate mapping needs no recursion.
object_therapy is stored JSON-quoted Matches therapy.key 0 % raw, 100 % unwrapped.
The data column is most of the file scv.data alone is ~15 GB uncompressed of a ~20 GB table. Column pruning is the whole performance story.

An existing interactive version of these diagrams is at https://claude.ai/artifact/TGKVvDkbH7FhE3xvYnu89v — use it as the content source for the two new diagram files, not as a drop-in asset (it carries its own palette; see Task 2).

Task 6: Create docs/parquet/joining.md — "Joining Sections"¶

Files: Create docs/parquet/joining.md

The core technical page. Embed parquet-join-seams.html, then one section per seam: the diagram strip, the runnable join, and the trap.

  • [x] Step 1: Seam A — Variant → Proposition. Four tables spell the subject column differently (subject_variant_id vs subject_id); UNION ALL them once into a prop CTE and reuse it.
  • [x] Step 2: Seam B — Proposition → Condition / ConditionSet. Branch on prefix: clinvar.trait: → condition, and both clinvar.traitset: and clinvar.conditionset: → conditionSet. LEFT JOIN both and keep a resolved_via flag so losses are visible rather than silent.
  • [x] Step 3: Expanding a set to member names — the trap worth its own callout. conditionSet.concepts[] holds ids, so array_to_string(concepts, …) prints clinvar.trait:2965, not a disease name. unnest and re-join to condition. Two further points: membershipOperator (AND/OR) changes what the set asserts and must travel as its own column, because array_to_string requires a constant separator; and a minted set can nest a clinvar.traitset: member, so expansion is one level deeper than it looks.
  • [x] Step 4: Seam C — Proposition → Statements. Label it 1:1 explicitly and show the three-table UNION ALL, noting each tier's shares sum to its exact row count.
  • [x] Step 5: Seam D — the aggregate group. Root cites children, children cite SCVs, SCVs are leaves.
  • [x] Step 6: Seam E — the efficient SCV ↔ aggregate mapping. The accession in the citing statement's own id names the group, so one pass over has_evidence_lines ⋈ evidence_items yields every pair with no recursion. Keep statement_id as well as the accession — it is what distinguishes -CP from -NOCP from -EP.
  • [x] Step 7: A "joins that lie" summary box — the four prefix-dispatched columns, gene_context_name on a non-unique natural key, and object_therapy needing trim(…, '"') plus prefix stripping.

Decisions this plan takes, and what it declines¶

A new tab, not a subsection of Downloads. Downloads was deliberately reshaped six days ago (2026-10-08-downloads-approachable-redesign.md) into a distribution hub with four scoped child pages. A seven-page learning track nested inside it would fight that design and bury the beginner entry point three levels deep. The parallel to draw is Data Guide, which is exactly this for JSON consumers.

data-access/parquet.md is not dismantled. It is new, it is linked from ten places, and its job — browsers, file table, stable URLs, deltas — is genuinely distribution. The new track links to it for "how do I get the files" and never duplicates the file table.

Deltas stay on the distribution page. Keeping a set current is a release-mechanics problem, not a query problem, and the existing content is good. The track cross-links it.

Not proposed here: moving the orphaned data-access/index.md, data-access/output-files.md, getting-started.md and output-reference/index.md into the nav. They are reachable only by direct link today. That is a real finding from this survey but it is a separate concern, and CLAUDE.md says touch only what the request covers — worth raising as its own issue.

Added at review: remote querying is now taught (reverses convention #5)¶

The custom domain data.clinvar-gkm.org/v1 (PR #138, CDN) serves HTTP range requests (accept-ranges: bytes) with CORS open (access-control-allow-origin: *), and DuckDB autoloads httpfs for https:// paths. Verified against the 14 Oct release:

Operation (remote) Result
count(*), DESCRIBE, schema footer-only, ~0.5 s even on 3 GB scv.parquet
Small sections; targeted / LIMIT reads on big files fast (~0.5 s)
Full-column scan / GROUP BY on a big file, default threads HTTP 429 — burst of parallel range requests (scv = 55 row groups, varcond = 223) trips Cloudflare's limiter
Same scan with SET threads=1 + retry/backoff completes (~18.5 s for the scv classification rollup)

Resolution — hybrid presentation. Remote (FROM 'https://data.clinvar-gkm.org/v1/datasets/parquet/00-latest/<section>.parquet') is the default for light work — Start Here, single-table, targeted lookups — where it is zero-friction and genuinely fast. Heavy work — the joins on Joining Sections, the big scans in Recipes — downloads once and queries local files. The range-request model, the 429 boundary, and the SET threads=1 + http_retries throttle are taught explicitly (in The 22 Sections / Working at Scale) as the reason for the split, not hidden. Base URL path: v1/datasets/parquet/00-latest/ (stable "latest"); dated pins at v1/datasets/parquet/<YYYY-MM>/.

Added at review: a live in-browser query console¶

Because the CDN sets access-control-allow-origin: *, a DuckDB-Wasm console embedded in the docs runs a reader's SQL against data.clinvar-gkm.org directly — no install, no download. It is built and lives at docs/assets/duckdb-console.html (theme-aware, same palette as the diagrams), embedded by <iframe> as the centerpiece of Start Here (Task 3): a reader queries real ClinVar data in their first 30 seconds. Guardrails: SET threads=1, a client-side one-query-per-10 s cooldown (greyed Run button + countdown), and example queries chosen to be light/reliable (the heavy full-scan lesson stays in prose). Errors are humanized (plain-language headline + what-to-do hint + collapsible raw details).

Runtime is vendored, not CDN-loaded (review decision). The eh bundle lives in docs/assets/vendor/duckdb/ (~35 MB: duckdb-eh.wasm + the eh worker verbatim, plus an esbuild-bundled duckdb-browser.bundled.js with apache-arrow inlined — the package ESM has an unresolvable bare import "apache-arrow"). Plain committed files (Git LFS can't be used — GitHub Pages serves the LFS pointer, not the file). The bundle is named .js not .mjs (GitHub Pages has served .mjs with a MIME type that breaks ESM imports). Provenance + the reproducible rebuild command are in that directory's README.md.

Cost (verified against the 14 Oct release): this is cheap by design — R2 egress is $0; the only query-driven cost is Class B reads ($0.36 / million, 10 M/month free), fenced by the console cooldown and the WAF rate-limit rule in ADR 0005. Big sections (>512 MB) never cache (BYPASS); 00-latest is set to bypass cache while dated paths cache (MISS→HIT) — a possible follow-up is to default the console to the newest dated release so small-section reads serve from the edge. No native hard spend cap exists, so a usage alert is the safety net (Cloudflare has no dedicated R2-ops alert type on the Free plan — a Custom Alert is the route).
