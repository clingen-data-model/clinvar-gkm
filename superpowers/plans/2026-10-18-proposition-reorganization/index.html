Proposition Reorganization by Meaning — Implementation Plan¶

For agentic workers: REQUIRED: Use superpowers:subagent-driven-development or superpowers:executing-plans. Steps use checkbox (- [ ]) syntax. Each PR in §8 is one reviewable unit. Run /catchup before starting a PR; this plan was written against main @ 567272c and 1.0 @ 6606d3d with the PR stack as of 2026-10-18. Every live BigQuery rebuild and every R2 write is a separately user-confirmed step.

Goal: Reorganize ClinVar-GKM propositions by meaning instead of object shape, in both the JSON bundle and the typed Parquet, in the current 1.x line, as part of the one consolidated rebuild and backfill (see the master plan 2026-10-16-parquet-followups.md, "Consolidated data release").

Decided (user, 2026-10-18):

  1. Four meaning-based groups replace varcond-proposition, varcustom-proposition, vartumor-proposition and vartherapy-proposition (§2).
  2. All proposition Parquet tables share one column schema, so read_parquet('proposition*.parquet') unions them with no renaming. Every column is derivable from the bundle (§4).
  3. It ships now under ADR 0004 §5 (in-place change during stabilization, announced), inside the single consolidated rebuild + backfill. Docs move with every PR.

Architecture (recommended): Keep the three per-level dict tables (gkm_dict_proposition, gkm_dict_rcv_proposition, gkm_dict_vcv_proposition) exactly as they are. Only two things change in BigQuery: the section name inside every statement and evidence-line pointer (#/<section>/<id>), and one canonical type→section function that every producer and the export share. The split into sections stays at the delivery layer (export + assemble), as Phase 2 did. Proposition ids, proposition records, the change log, the delta build and both oracles are untouched by the reorganization itself.

Consequence: every SCV, VCV and RCV statement and every SCV evidence line changes (its pointer), so the patch-style backfill prepared for 1.0.2 (scratchpad/backfill102/) no longer fits. The release becomes a full rebuild of all 16 datasets + full re-export + re-assembly of every published bundle and Parquet set, modeled on 1.0.1 (§6).

Source: Counts were measured read-only on clinvar_2026_09_28_v2_6_0 (source of the 2026-10 monthly) and clinvar_2026_10_11_v2_6_0, and type coverage across all 16 published-release datasets. Parquet sizes are from a prototype that rebuilt the four new tables from the published 2026-10 Parquet data column (the bundle record) with DuckDB, calibrated against the published files (§5).

2. The groups¶

2.1 Coverage check¶

Every proposition type in all 16 datasets behind published releases (clinvar_2026_06_27_v2_5_0 … clinvar_2026_10_11_v2_6_0, SCV + RCV + VCV dicts, 91 GB scanned) falls into exactly one group. 15 types occur:

Type Levels seen New section
VariantPathogenicityProposition SCV, RCV, VCV propositionPathogenicity
ClinvarNotProvidedProposition, ClinvarDrugResponseProposition, ClinvarOtherProposition, ClinvarRiskFactorProposition, ClinvarAssociationProposition, ClinvarAffectsProposition, ClinvarConflictingDataFromSubmitterProposition, ClinvarProtectiveProposition, ClinvarConfersSensitivityProposition SCV, RCV, VCV propositionClinvarCustom
VariantClinicalSignificanceProposition SCV, RCV, VCV propositionSomaticClinicalImpact
VariantDiagnosticProposition, VariantPrognosticProposition, VariantTherapeuticResponseProposition SCV only (evidence-line targets) propositionSomaticClinicalImpact
VariantOncogenicityProposition SCV, RCV, VCV propositionOncogenicity

Stragglers:

  • ClinvarUndefinedProposition: 0 rows in all 16 datasets, but reachable. The SCV proc falls back to it when a classification has no type (gkm-scv-statement-proc.sql Step 1, the STRUCT('ClinvarUndefinedProposition' …) arm), and the RCV/VCV dict builds use IFNULL(cpt.gks_type, 'ClinvarUndefinedProposition'). The lookup table clinvar_ingest.clinvar_proposition_types also has an undef row. → propositionClinvarCustom (it is a Clinvar* custom type and is already in the custom section's schema anyOf).
  • ClinvarGermlineCustomProposition: 0 rows. It is the abstract base the custom types compose, never a type value. It gets no section. It should also leave the custom section's anyOf in the bundle schema (today it is listed there, which lets a custom-shaped record with a wrong type pass); coordinate with #153, which reworks those mixins.
  • VCV/RCV: there are no VCV/RCV-only types. Diagnostic, Prognostic and TherapeuticResponse never occur above SCV; VCV/RCV somatic aggregates use VariantClinicalSignificanceProposition, which lands in the same group as the SCI SCVs they aggregate.

Latent gap (fix in this release): the RCV/VCV statement pointer sites compute the group from cpt.gks_type without the IFNULL. A NULL type would hit the ELSE ERROR, so it fails loudly today. The new canonical function (§2.3) takes the same resolved type the dict row carries, so a future Undefined row gets a consistent pointer.

2.2 Names¶

Existing bundle sections are lowerCamelCase nouns (sequenceReference, copyNumberChange, conditionSet, therapyGroup, evidenceLine). The four *-proposition keys are the only kebab-case sections, so the reorg also removes an inconsistency.

Option Example For Against
proposition<Meaning> (proposed) propositionPathogenicity lowerCamelCase like every other section; sorts together in listings and the R2 browser; proposition*.parquet is one glob; a pointer test is startsWith('#/proposition') reads noun-first
<meaning>Proposition pathogenicityProposition mirrors the va-spec class names scatters alphabetically; the glob becomes *Proposition.parquet

Recommendation: keep the proposed names: propositionPathogenicity, propositionClinvarCustom, propositionSomaticClinicalImpact, propositionOncogenicity. The Parquet file names equal the section names (as every other section's do), so read_parquet('proposition*.parquet') matches exactly these four and nothing else.

Section order in the bundle (assembler SECTIONS, in place of the four current entries): propositionPathogenicity, propositionOncogenicity, propositionSomaticClinicalImpact, propositionClinvarCustom.

2.3 One canonical mapping¶

Today the type→group CASE is copied verbatim into 11 places (8 proc sites, the NDJSON export, the delta manifest, the conformance validator) and the Parquet SQL uses four separate WHERE filters. Copies can drift, and the WHERE filters silently drop an unmapped type from Parquet while the NDJSON export raises (Parquet-vs- bundle audit, finding 1).

Recommendation: one persistent SQL UDF, versioned in this repo and deployed with the procs:

-- src/procedures/gkm-proposition-section-func.sql
CREATE OR REPLACE FUNCTION `clinvar_ingest.gkm_proposition_section`(prop_type STRING) AS (
  CASE
    WHEN prop_type = 'VariantPathogenicityProposition' THEN 'propositionPathogenicity'
    WHEN prop_type = 'VariantOncogenicityProposition' THEN 'propositionOncogenicity'
    WHEN prop_type IN ('VariantClinicalSignificanceProposition', 'VariantDiagnosticProposition',
                       'VariantPrognosticProposition', 'VariantTherapeuticResponseProposition')
      THEN 'propositionSomaticClinicalImpact'
    WHEN prop_type IN ('ClinvarNotProvidedProposition', 'ClinvarDrugResponseProposition',
                       'ClinvarOtherProposition', 'ClinvarRiskFactorProposition',
                       'ClinvarAssociationProposition', 'ClinvarAffectsProposition',
                       'ClinvarConflictingDataFromSubmitterProposition', 'ClinvarProtectiveProposition',
                       'ClinvarConfersSensitivityProposition', 'ClinvarUndefinedProposition')
      THEN 'propositionClinvarCustom'
    ELSE ERROR(FORMAT('unmapped proposition type for section mapping: %t', prop_type))
  END
);
  • The custom list is explicit (not LIKE 'Clinvar%'), so a new upstream type fails the build instead of landing in a section whose schema rejects it.
  • Every consumer calls it: the 8 pointer sites, the NDJSON export, the Parquet template's WHERE, the delta manifest and the validator. In the Parquet export the WHERE evaluates the function on every row, so an unmapped type raises and fails the export: the same fail-loud behavior as NDJSON.
  • It lives under src/procedures/, so it is part of run-release.sh's gate_key (git log -1 -- src/procedures src/scripts src/vrsify).
  • Belt and braces: the export also asserts that the four sections' row counts sum to the three dicts' total.

3. Pending decisions¶

3.A Gene-context qualifier: keep it on the proposition (revised)¶

Not planned: moving submittedGeneSymbols to the SCV statement, or dropping the placeholder qualifiers. The user's direction (2026-10-18): propositions must capture the geneContextQualifier, because the submitter's stated gene is the strongest evidence of the gene context of the claim.

  • submittedGeneSymbols stays an extension on the qualifier.
  • The Parquet submitted_gene_symbols, gene_context_id and gene_context_name stay on the proposition tables (PR #143 adds them; the shared schema in §4 carries them on all four tables).
  • The placeholder qualifiers stay.

Measured facts (2026-09-28, 6,736,579 SCV propositions; the six cases sum to the total):

Case SCV propositions
Submitter's gene equals the qualifier gene 5,781,673
Submitter gave this gene plus others 101
Submitter's gene differs from the qualifier gene (top cases are old or renamed symbols for the same gene: GBA→GBA1, MUT→MMUT, C10orf2→TWNK, CENPJ→CPAP) 27,817
Gene inferred from the variant (single_gene_variation); submitter gave none 881,325
Placeholder: submitter gave a gene, the variant has no single gene (name = "submitted genes were not normalized") 4,814
No qualifier 40,849

Candidate improvements (the user's to decide):

  • (a) a provenance extension on the qualifier: the gene came from the submitter, was inferred, or differs;
  • (b) the placeholder's name set to the submitted symbol verbatim, plus a not-normalized flag, instead of the literal "submitted genes were not normalized";
  • (c) submitter-first selection of the qualifier gene.

VCV/RCV propositions carry no geneContextQualifier today (C4 keeps it SCV-only); the shared Parquet columns are NULL on those rows.

Does the reorganization affect this? No. The qualifier lives inside the proposition record; the reorg changes only which section the record sits in and the pointer prefix. The record and its id are unchanged.

Timing constraint: (a), (b) and (c) all change SCV proposition records. Under the single-rebuild rule they must be decided before the rebuild in §6, or deferred to a later release that ships forward-only (new releases only, no backfill). Deciding one of them after the backfill would force a second backfill. (a) and (b) are additive or value-only; (c) changes which gene 27,817 propositions name, a semantic change that would need its own announcement.

Resolved (2026-10-18): (a) + (b) in this release, (c) deferred. Implemented in #159 (1.0, SCV proc Step 2), so they ride the single rebuild:

  • (a) every geneContextQualifier carries a geneContextSource extension: submittedSymbolMatches, submittedSymbolDiffers, inferredFromVariant or submittedNotNormalized. Symbols are compared trimmed and case-insensitively, which moves 146 case-only differences (C19ORF12 vs C19orf12) from "differs" to "matches". On 2026-09-28 the counts are 5,781,920 / 27,671 / 881,325 / 4,814, plus 40,849 propositions with no qualifier.
  • (b) the placeholder's name is the submitter's symbol. The 5 multi-symbol placeholders join the symbols with ", " in submitted order. There is still no primaryCoding, and submittedGeneSymbols stays. The submittedNotNormalized value is the not-normalized flag.

  • 159 also gives submittedGeneSymbols a total (submitted) order. ARRAY_AGG(DISTINCT) had left 45¶

    multi-symbol lists to flip order between runs. It also trims the leading space our comma split left (" MEG3"; 3 propositions).
  • The shared Parquet schema gains gene_context_source (§4.1); #143 adds it to the four current tables.

3.B Content-shared propositions: defer¶

Measured (memory project_proposition_content_dedup, 2026-08-16; and 2026-10-18 notes): VCV and RCV propositions are about 50% exact-content duplicates; SCV dedup tops out at 10–13%. Today no proposition is shared at any level (SCV/VCV/RCV are all 1:1 with statements).

Confirmed in the procs: the incremental VCV/RCV carry-forward recovers the parent accession from the proposition key:

  • gkm-vcv-statement-proc.sql:35 (contract) and :708, :710 — SPLIT(b.key, '-')[OFFSET(0)] decides which baseline rows to carry forward (accession not impacted) and drops rows of removed VCVs;
  • gkm-rcv-statement-proc.sql:38 and :702, :704 — the same for RCVs.

SCV propositions are recomputed globally every release (gkm-scv-statement-proc.sql header, Step 7e), so they do not depend on this parse; the per-SCV outputs parse clinvar.submission: ids instead.

Consequence of content-addressed ids:

  • the VCV/RCV carry-forward breaks: a shared key names no accession, so the merge needs a statement→proposition join and reference counting;
  • delta tombstones need garbage collection: a shared proposition can be deleted only when no statement uses it;
  • the change log sees every proposition key change once (a full churn delta);
  • build-delta-manifest.py assumes "each key encodes its type code"; sub-bundle.py routes propositions by key prefix (SCV/VCV/RCV); the bundle schema's patternProperties is ^(SCV|VCV|RCV).+;
  • consumers that read the level from the id prefix break.

The size win is small: about 2.9 GB uncompressed, 4.7% of the statement+proposition core, less gzipped. Recommendation: defer, as decided on 2026-09-29. The reorganization keeps ids unchanged, so it neither helps nor blocks a later dedup.

3.D New: normalize VCV object and vcv- set members (found while measuring)¶

Decided (user, 2026-10-18): (i). It is its own PR, #160 (branch fix/uniform-condition-pointers, base 1.0), not part of PR 1–4. The re-wrap is done at emission in gkm-vcv-statement-proc.sql (the three obj_ref builds and the synthetic vcv- set concepts), not in gkm-vcv-proc.sql's condition_ref: the vcv- id digest stays over the bare CURIEs, so no vcv- id changes, and the gkm_vcv_*_agg tables are untouched. On 2026-10-11 it rewrites 7,474,404 VCV propositions and all 94,980 vcv- sets; 0 bare references and 0 dangling pointers remain; the Parquet typed id columns are unchanged. The text below is the original analysis.

The bundle mixes reference forms for the same kind of target:

Where Form Count (2026-10-11)
SCV and RCV proposition object #/condition/… or #/conditionSet/… pointer all rows
VCV proposition object, single condition bare CURIE clinvar.trait:… / clinvar.traitset:… 7,474,404 of 9,156,181
VCV proposition object, several conditions #/conditionSet/clinvar.conditionset:vcv-… pointer 1,681,777
traitset ConceptSet members #/condition/ pointers 5,345 sets (audit)
pipeline vcv- ConceptSet members bare ids 83,538 sets (audit)
therapyGroup members #/therapy/ pointers all

Cause: the 1.0.0 submittedCondition de-pointer turned the extension's condition/conditionSet into bare CURIEs. The SCV and RCV consumers re-wrap them into pointers; gkm-vcv-proc.sql (vcv_conditions, condition_ref) does not, so VCV propositions and the synthetic vcv- sets carry them bare. Both validate (a string is a valid iriReference), but the bundle schema's description promises #/<section>/<id> cross- references, and a consumer resolving pointers misses 7.5 M VCV objects.

Options:

  • (i) Normalize now (recommended): in gkm-vcv-proc.sql wrap condition_ref as #/condition/ + clinvar.trait: / #/conditionSet/ + clinvar.traitset: (the same re-wrap the SCV/RCV procs use), and build the vcv- set concepts as #/condition/ pointers. Every VCV row is rewritten in this rebuild anyway, so the marginal cost is the review and the oracle. The Parquet object_id is bare either way; object_type becomes pointer-derived.
  • (ii) Leave as is: the shared Parquet derives object_type from the CURIE prefix as a fallback (§4.2). Document the mixed forms on Joining Tables.

Also found: 4 RCV propositions have no object (all on RCV000001117, since 2026-10-04; 2 Pathogenicity, 2 NotProvided). va-spec requires object, so these fail validation in the published 2026-10-04 delta; the 1.0.1 toolkit gate covered only the 2026-10-11 delta and a full. Trace the cause in the RCV proc (likely an RCV whose condition no longer resolves) before the rebuild, and run the toolkit gate on every published bundle (§6.4).

4. The shared Parquet schema¶

4.1 Columns¶

All four tables have exactly these columns, in this order; non-applicable columns are NULL. Each column cites the bundle path it derives from (user rule: Parquet holds only bundle-derivable values).

Column Type Bundle source Notes
id VARCHAR section key (= $.id) unchanged ids
type VARCHAR $.type
predicate VARCHAR $.predicate
subject_variant_id VARCHAR $.subject, pointer stripped was subject_id on varcustom
object_id VARCHAR $.object, pointer stripped was object_condition_id / object_tumor_type_id / object_therapy
object_type VARCHAR $.object pointer section (CURIE prefix as fallback) condition, conditionSet, therapy, therapyGroup
condition_qualifier_id VARCHAR $.conditionQualifier, stripped TherapeuticResponse only
gene_context_id VARCHAR 'ncbigene:' ‖ $.geneContextQualifier.primaryCoding.code from #143; NULL on placeholders
gene_context_name VARCHAR $.geneContextQualifier.name
submitted_gene_symbols VARCHAR[] the submittedGeneSymbols extension on the qualifier from #143
gene_context_source VARCHAR the geneContextSource extension on the qualifier, picked by name from #143 / #159 (decision A)
mode_of_inheritance VARCHAR $.modeOfInheritanceQualifier.name germline SCV only
penetrance VARCHAR $.penetranceQualifier.name germline SCV only
data VARCHAR the whole record, collapse_ext_values applied last, as in every table

There is no tumor-type section. Oncogenicity objects are condition / conditionSet records, so object_type has four values. (vartumor-proposition.object_tumor_type_id was already a condition id.)

4.2 The template¶

One schema file replaces the four (parquet-schemas/proposition.sql, with a {SECTION} placeholder that extract_parquet_typed substitutes). The data expression is unchanged from today, so neither strip path moves (audit note 3: BigQuery JSON_STRIP_NULLS drops empty array elements at dict-build time; the assembler's Python strip_empty keeps them; the reorg touches neither).

-- One shared column schema for every proposition section ({SECTION}). Unions the SCV/RCV/VCV dicts.
-- The WHERE calls the canonical section function, which raises on an unmapped type (fail loud).
SELECT
  key AS id,
  JSON_VALUE(value, '$.type') AS type,
  JSON_VALUE(value, '$.predicate') AS predicate,
  REGEXP_REPLACE(JSON_VALUE(value, '$.subject'), r'^#/[^/]+/', '') AS subject_variant_id,
  REGEXP_REPLACE(JSON_VALUE(value, '$.object'), r'^#/[^/]+/', '') AS object_id,
  CASE
    WHEN JSON_VALUE(value, '$.object') IS NULL THEN NULL
    WHEN STARTS_WITH(JSON_VALUE(value, '$.object'), '#/')
      THEN REGEXP_EXTRACT(JSON_VALUE(value, '$.object'), r'^#/([^/]+)/')
    WHEN STARTS_WITH(JSON_VALUE(value, '$.object'), 'clinvar.trait:') THEN 'condition'
    WHEN STARTS_WITH(JSON_VALUE(value, '$.object'), 'clinvar.traitset:') THEN 'conditionSet'
    ELSE ERROR(FORMAT('unrecognized proposition object: %t', JSON_VALUE(value, '$.object')))
  END AS object_type,
  REGEXP_REPLACE(JSON_VALUE(value, '$.conditionQualifier'), r'^#/[^/]+/', '') AS condition_qualifier_id,
  IF(JSON_VALUE(value, '$.geneContextQualifier.primaryCoding.code') IS NULL, NULL,
     CONCAT('ncbigene:', JSON_VALUE(value, '$.geneContextQualifier.primaryCoding.code'))) AS gene_context_id,
  JSON_VALUE(value, '$.geneContextQualifier.name') AS gene_context_name,
  ARRAY(
    SELECT JSON_VALUE(sym)
    FROM UNNEST(JSON_QUERY_ARRAY(value, '$.geneContextQualifier.extensions')) AS ext,
         UNNEST(JSON_QUERY_ARRAY(ext, '$.value_string')) AS sym WITH OFFSET so
    WHERE JSON_VALUE(ext, '$.name') = 'submittedGeneSymbols'
    ORDER BY so
  ) AS submitted_gene_symbols,
  (
    SELECT JSON_VALUE(ext, '$.value_enum')
    FROM UNNEST(JSON_QUERY_ARRAY(value, '$.geneContextQualifier.extensions')) AS ext
    WHERE JSON_VALUE(ext, '$.name') = 'geneContextSource'
  ) AS gene_context_source,
  JSON_VALUE(value, '$.modeOfInheritanceQualifier.name') AS mode_of_inheritance,
  JSON_VALUE(value, '$.penetranceQualifier.name') AS penetrance,
  collapse_ext_values(TO_JSON_STRING(value)) AS data
FROM (
  SELECT key, value FROM `{DATASET}.gkm_dict_proposition`
  UNION ALL SELECT key, value FROM `{DATASET}.gkm_dict_rcv_proposition`
  UNION ALL SELECT key, value FROM `{DATASET}.gkm_dict_vcv_proposition`
)
WHERE `clinvar_ingest.gkm_proposition_section`(JSON_VALUE(value, '$.type')) = '{SECTION}'
  • 3.D (i) is decided (#160): drop the two CURIE fallback arms so a non-pointer object fails the export.
  • The delta export's .gkm_dict_ → .delta_gkm_dict_ rewrite (export-gkm-dicts.sh:112-118) works unchanged: the template references the three dicts, each with a delta_ counterpart (the invariant comment as corrected by #143 c4cabeb).
  • submitted_gene_symbols is an empty array, not NULL, where there is none (same as #143). Pick one and document it; NULL is easier to test and matches "non-applicable columns are NULL".

6. Release mechanics¶

6.1 Why a full rebuild¶

The pointer strings live in the stored statement and evidence-line dicts (gkm_dict_scv, gkm_dict_vcv, gkm_dict_rcv, gkm_dict_evidence_line) of every dataset. Every statement changes, so every published bundle and every statement and proposition Parquet file changes. The 1.0.2 patch scripts swapped 14 variation lines per full; they cannot rewrite every statement.

A pointer-only SQL rewrite of the four dict tables in 16 datasets would be cheaper, but A1 (catvar), the citation fix (SCV statement proc), the allele duplicate-key fix and 3.D (VCV proc) need the procs to run anyway. One proc-level rebuild is simpler to reason about and to oracle-gate. Recommendation: full rebuild, the proven #132 / 1.0.1 path.

7.2 Querying old and new releases together (DuckDB)¶

Every published release is re-written, so R2 serves only the new layout. Local copies downloaded earlier keep the old one. Because both layouts keep the full record in data, the new shape can be rebuilt from either:

-- New layout (1.1.0 and later): one glob, one schema.
SELECT * FROM read_parquet('proposition*.parquet');

-- Old layout (local copies from before 1.1.0): rebuild the new shape and section from `data`.
CREATE OR REPLACE MACRO bare(p) AS regexp_replace(p, '^#/[^/]+/', '');
CREATE OR REPLACE VIEW proposition_old AS
SELECT
  j->>'$.id' AS id, j->>'$.type' AS type, j->>'$.predicate' AS predicate,
  bare(j->>'$.subject') AS subject_variant_id,
  bare(j->>'$.object') AS object_id,
  CASE WHEN j->>'$.object' LIKE '#/%' THEN regexp_extract(j->>'$.object', '^#/([^/]+)/', 1)
       WHEN j->>'$.object' LIKE 'clinvar.trait:%' THEN 'condition'
       WHEN j->>'$.object' LIKE 'clinvar.traitset:%' THEN 'conditionSet' END AS object_type,
  bare(j->>'$.conditionQualifier') AS condition_qualifier_id,
  CASE WHEN j->>'$.geneContextQualifier.primaryCoding.code' IS NOT NULL
       THEN 'ncbigene:' || (j->>'$.geneContextQualifier.primaryCoding.code') END AS gene_context_id,
  j->>'$.geneContextQualifier.name' AS gene_context_name,
  CAST(list_filter(CAST(j->'$.geneContextQualifier.extensions' AS JSON[]),
                   lambda e: e->>'$.name' = 'submittedGeneSymbols')[1]->'$.value' AS VARCHAR[]) AS submitted_gene_symbols,
  list_filter(CAST(j->'$.geneContextQualifier.extensions' AS JSON[]),
              lambda e: e->>'$.name' = 'geneContextSource')[1]->>'$.value' AS gene_context_source,
  j->>'$.modeOfInheritanceQualifier.name' AS mode_of_inheritance,
  j->>'$.penetranceQualifier.name' AS penetrance,
  data,
  CASE WHEN j->>'$.type' = 'VariantPathogenicityProposition' THEN 'propositionPathogenicity'
       WHEN j->>'$.type' = 'VariantOncogenicityProposition' THEN 'propositionOncogenicity'
       WHEN j->>'$.type' LIKE 'Clinvar%' THEN 'propositionClinvarCustom'
       ELSE 'propositionSomaticClinicalImpact' END AS section
FROM (
  SELECT data, data::JSON AS j
  FROM read_parquet(['varcond-proposition.parquet', 'varcustom-proposition.parquet',
                     'vartumor-proposition.parquet', 'vartherapy-proposition.parquet'], union_by_name = true)
);

(Extensions are picked by name: from decision A the qualifier can carry two, so extensions[0] is no longer safe. lambda e: needs DuckDB 1.3 or later. gene_context_source is NULL in releases before #159.) The same expressions reproduce the new tables exactly: they are the §5.2 prototype.

10. Risks and open questions¶

Risks

  1. Stale sections on R2. Dated Parquet directories are never wiped, and the index lists sections from the R2 listing. Without PR 4's wipe plus the explicit delete, every release would list eight proposition tables (four dead). Gate: index section lists equal the expected 22.
  2. Allele non-determinism. Independent full rebuilds pick different duplicate-key alleles (1.0.1 follow-up), which reappears as allele oracle failures and spurious allele changes in republished releases unless the tie-breakers land first.
  3. A second rebuild. Any data decision left open (3.A (c), 3.D, E, C1-driven bundle additions) that is taken after the backfill forces another full backfill. Settle them first, or explicitly defer them as forward-only.
  4. Weekly releases in the window. A weekly run from 1.0 after the merges and before the backfill would publish the new layout on top of unpatched history. Pause the weekly runs.
  5. Disk and stalls. About 15 GB free against a 4.8 GB full plus about 12 GB Parquet per monthly set; bq poll hangs seen in 1.0.1. Run one full at a time with a watchdog.
  6. Consumer breakage. Every section, table and three column names change, and every published file is rewritten. The advance announcement and §7 are the mitigation; the stabilization window is the justification.
  7. Schema-invalid records already published. The 4 object-less RCV propositions in the 2026-10-04 delta (§3.D). The all-bundles toolkit gate catches this class; fix the cause before the rebuild.
  8. Version label churn. C = 1.1.0, and three open PRs carried 1.0.2 (now relabelled); a missed string makes $ids or schema_version disagree. Gate: grep -r 1.0.2 schema src = 0 before tagging.
