ClinVar-GKM 1.2.0 release: runbook¶

Status: prepared 2026-11-18; decisions D1–D6 approved 2026-11-18; step 1 done (#225 merged, 788ef82). Steps marked [OK] touch BigQuery, GCS/GCP, live R2, Cloudflare, a tag, a merge, or an email, and run only after the maintainer confirms that step. Never touch live R2 without that confirmation; dry-run first wherever a script offers it. Never print the R2 or Cloudflare credentials.

Scope. 1.2.0 = the narrowed profiles (#215, on main) plus the aggregate VCV/RCV primaryCoding, strength and direction fixes (#225, fixes #202, #226, #227). As a MINOR it opens a new R2 line, v1/1.2/ (ADR 0009 §1, §5), and freezes v1/1.1/ (ADR 0008 (b), (c)). Maintainer decisions of 2026-11-18:

  1. v1/1.2/ starts with one checkpoint monthly (the first 1.2.0 full) plus deltas forward. No republish of history.
  2. At the freeze, v1/1.1/ loses its weekly fulls and its parquet/; its monthlies, 00-latest, archive and deltas stay, frozen forever, no eol.
  3. Superseded lines are frozen forever.
  4. Parquet publishing stays on hold (--skip-parquet) until #217 lands with gkm-bundle-parquet 2.0.0.

Tooling (PR "feat(r2): v1/1.2 line, checkpoint bootstrap and line freeze"): r2_layout.LINES / CURRENT_LINE, R2_LINE defaults v1/1.2/, run-release.sh --bootstrap-monthly=YYYY-MM, the first-delta chain check in r2_layout.py patch-manifest, and r2-freeze-line.sh (dry run by default).

Decisions (approved 2026-11-18)¶

  • D1. The checkpoint: v1/1.2/clinvar-gkm_2026-11.json.gz ← 2026-10-31, rebuilt with the 1.2.0 procs. It is the ADR 0002 monthly for 2026-11, so the label is honest, and the two lines meet at the same ClinVar state. The 1.2 deltas then run 2026-11-08, 2026-11-15, … (never published in 1.1). The docs examples in this PR assume it.
  • D2. Yes: a final 2026-11 monthly in v1/1.1/, a server-side copy of the 1.1 weekly full 2026-10-31 (no build, no BigQuery), done from the 1.0 code before step 4 rebuilds 2026-10-31 and before the freeze deletes the weekly (step 2). The automated announcement is accepted: within about 2 h, announce-monthly.yml emails the list and posts a Discussion for 2026-11 (1.1 line, digest 10-04..10-31). That also keeps the 1.2 checkpoint from being auto-announced (2026-11 is then in announced.json).
  • D3. Freeze with --keep-parquet (step 9), and run the freeze again without it once v1/1.2/parquet/ is published (step 13). The data stays, but from step 8 the DuckDB console follows the root index to v1/1.2 and is empty until the 1.2 Parquet set is published: there is no console change, so run step 13 immediately after step 8. With #217 based on release/1.2.0 (merging it needs the maintainer's OK), Parquet ships with 1.2.0.
  • D4. #229 merges to main after #228 (versioned docs). Its pages, which give v1/1.2/ URLs that 404 until step 8, then show only on dev, not in the released 1.1 docs.
  • D5. No 1.1 weeklies for November. 2026-11-08 and later become the first 1.2 deltas.
  • D6. ADR amendment in the release PR. ADR 0009 §1 says nothing is deleted from a frozen line, and ADR 0008 (b) describes a new line built in full. D1 and D2 + the freeze change both; the amendment goes in the release PR (step 3).

Steps¶

Gate checks follow each step. "Rollback" says how to undo it.

0. Pre-flight (read-only)¶

  • [ ] No release on the 1.0 branch until step 3 has merged main into it (no 1.0.x or other tag published as a GitHub Release from 1.0). The release: published event runs the workflow file at the tag; 1.0 still has the old whole-site deploy-docs.yml, which builds the tag's docs and publishes them with peaceiris without keep_files. That would replace all of gh-pages: 1.1/, dev/, versions.json and the root redirects would be gone, and the site would serve the 1.0 tree's unversioned docs (the pre-1.1 v1/datasets/… URLs, which 404). Recovery would be a dispatch of dev and of 1.1. A tag pushed without a GitHub Release doesn't trigger the workflow, but don't push one either: it is a release tag in name.
  • [ ] The release tag's docs must describe the line being shipped. Root cause of the 2026-11-19 docs incident: 1.1.0 was tagged on 1.0 without main's 1.1.0 docs, so the tag's pages gave the pre-1.1 v1/datasets/… URLs and no 1.1.0 changelog section; the 1.1 docs are now built from main@036bec2 instead (src/scripts/docs-line-sources.txt, ADR 0011 §6). For 1.2.0, step 3 merges main into the release branch; before the tag (step 7), check on origin/1.0: git grep -l 'v1/1\.2/' origin/1.0 -- docs lists the download pages, git grep -l 'v1/datasets' origin/1.0 -- docs ':!docs/superpowers' is empty, and docs/reference/changelog.md has the ## 1.2.0 — <date> section.
  • [ ] gh pr view 225 --json state,mergeable; CI green; #225 body: scratch rebuild 0,0,0.
  • [ ] bq ls --max_results=100000 | grep -E 'clinvar_2026_1[01]_': the datasets after 2026-10-31 and their version suffix; confirm 2026-10-31's suffix (e.g. v2_6_1), and that no dataset dated 11-01..11-04 has gkm_pipeline_version (else D1's source changes).
  • [ ] curl -s https://data.clinvar-gkm.org/v1/1.1/index.json: latest_release still 2026-10-31, no 2026-11 monthly; curl -sI .../v1/1.2/index.json is 404 (the line is empty).
  • [ ] src/scripts/r2-freeze-line.sh v1/1.1/ (dry run, read-only listing): no PROBLEM; keeps 41 files.
  • [ ] Cost quote for steps 4–5 (BigQuery): the full procs on 2026-10-31 plus each catch-up release; announce it.

1. Merge #225 into main [OK: merge] — DONE 2026-11-18 (merge commit 788ef82)¶

Gate: main CI green; git log origin/main -1 is the merge. Rollback: revert the merge commit.

2. (D2 = yes) Post v1/1.1/'s final monthly 2026-11 [OK: live R2, triggers the automated email]¶

From a checkout of origin/1.0 (old code: CURRENT_LINE is still v1/1.1/, so the root index stays right):

R2_LINE=v1/1.1/ src/scripts/upload-gkm-to-r2.sh 2026-10-31 <ver> - --month-label=2026-11 --from-weekly --dry-run
R2_LINE=v1/1.1/ src/scripts/upload-gkm-to-r2.sh 2026-10-31 <ver> - --month-label=2026-11 --from-weekly

Gate: v1/1.1/index.json lists 2026-11 with source_release 2026-10-31 and 00-latest → 2026-11; its sha256 is the weekly 2026-10-31's. Within ~2 h the announcement workflow run succeeds (email + Discussion). Rollback: none needed (a correct, immutable record); do not delete it.

3. Release branch off 1.0 [OK: PR merge into 1.0]¶

git fetch origin
git switch -c release/1.2.0 origin/1.0
git merge --no-ff origin/main          # merge commit, never a squash

In the same PR: changelog ## Unreleased → ## 1.2.0 — <date>; CITATION.cff version/date-released; the ADR amendment (D6). Gate: pytest src/scripts/tests; bash -n + shellcheck on src/scripts/*.sh; zensical build --clean --strict + check-site-links.py; git diff origin/main release/1.2.0 -- src schema is empty. Merge into 1.0. Rollback: revert the merge on 1.0 (nothing published yet).

From here on, run every release script from 1.0. Its CURRENT_LINE is v1/1.2/, so any index regeneration now writes a root index with current: v1/1.2 — no 1.1 step may run from it except the freeze (step 9).

4. Deploy the procedures [OK: BigQuery]¶

The set is git diff --name-only 1.1.0 origin/1.0 -- src/procedures (the #218 SQL guards and #225's gkm-vcv-proc.sql, gkm-vcv-statement-proc.sql, gkm-rcv-proc.sql, gkm-rcv-statement-proc.sql, and any other file listed). bq query --dry_run each, then deploy in dependency order (bq query --use_legacy_sql=false < file). Gate: every deployed routine body equals origin/1.0 (INFORMATION_SCHEMA.ROUTINES, as in the 1.1.0 runbook §1). Rollback: redeploy the same files from tag 1.1.0.

5. Build the first 1.2.0 full and the first delta (no upload) [OK: BigQuery spend]¶

The proc gate key changed, so the checkpoint is a full proc rebuild. vrsify is unchanged, so start at stage 4:

# Checkpoint: rebuild 2026-10-31 with the 1.2.0 procs (stage 4 also re-stamps gkm_pipeline_version)
src/scripts/run-release.sh 2026-10-31 --full-procs --start-step 4 --skip-parquet --bootstrap-monthly=2026-11 --dry-run

--dry-run runs stage 4 for real (BigQuery) and only prints stage 5: it checks the line is empty, that ClinVar's 2026-11 source is 2026-10-31, and prints the build and upload it would do. Then stage the bundle:

src/scripts/release-gkm.sh 2026-10-31 <ver> --month-label=2026-11 --no-upload     # export, assemble, rs-validate
# The 2026-10-31 delta of this build (baseline 2026-10-24, still 1.1.0 content): staged and validated with the
# toolkit as a sample of 1.2.0 records, NEVER published (it has no monthly to replay onto in v1/1.2/)
src/scripts/release-gkm-delta.sh 2026-10-31 <ver> --no-upload

Gate ("validate"): validate-bundle.sh <full> --engine rs = 0 failures (release-gkm.sh runs it); the delta's toolkit validation = 0 failures (release-gkm-delta.sh runs it); the full carries "schema_version": "1.2.0" and the #225 fields (a VCV aggregate classification with primaryCoding in the staged full). The first publishable 1.2 delta (2026-11-08, baseline 2026-10-31) is built and toolkit-validated by its own run in step 8, before anything uploads. Rollback: rebuild 2026-10-31 with the 1.1.0 procs (nothing was published).

6. Advance notice (ADR 0008 (g)) [OK: email + Discussion]¶

By hand (ADR 0010: version releases are announced by hand): email clinvar-gkm@broadinstitute.org from the service mailbox and post in Discussions → Announcements. Content: 1.2.0 (narrowed profiles, aggregate coding), the new v1/1.2/ line starting at the 2026-11 checkpoint, v1/1.1/ frozen (weekly fulls and Parquet removed), the URL change, the date of steps 8–9, and that Parquet returns with gkm-bundle-parquet 2.0.0. Gate: the post is live.

7. Tag 1.2.0 on 1.0 [OK: tag + GitHub Release]¶

git tag -a 1.2.0 origin/1.0 -m "ClinVar-GKM 1.2.0" && git push origin 1.2.0
gh release create 1.2.0 --target 1.0 --title "1.2.0" --notes-file <changelog 1.2.0 section>

Gate: curl -sI https://w3id.org/clingen/schema/clinvar-gkm/1.2.0/clinvar-gkm-bundle.schema.json → 200 (via raw.githubusercontent); git describe origin/1.0 = 1.2.0. Rollback: none (never move a pushed tag); a defect found later ships as 1.2.1 (new files only) or a new line.

8. Start v1/1.2/ with the checkpoint monthly, then catch up [OK: live R2]¶

src/scripts/run-release.sh 2026-10-31 --start-step 5 --skip-parquet --bootstrap-monthly=2026-11 --dry-run
src/scripts/run-release.sh 2026-10-31 --start-step 5 --skip-parquet --bootstrap-monthly=2026-11

It refuses unless v1/1.2/ is empty and 2026-10-31 is ClinVar 2026-11's source, then exports, validates (rs) and uploads v1/1.2/clinvar-gkm_2026-11.json.gz + .sha256 + 00-latest, README.txt, index.json, feed.xml and the root index.json (now current: v1/1.2, 1.1 frozen). No weekly full and no delta for 2026-10-31.

Gate: root current = v1/1.2; v1/1.2/index.json has monthly 2026-11, source_release 2026-10-31, schema_version 1.2.0, 00-latest = 2026-11; the sidecar sha256 equals the staged file's. Then publish each release after 2026-10-31 in date order (each a normal run; the first delta is refused unless its baseline is 2026-10-31):

# For each release after 2026-10-31, oldest first (stage 3, vrsify, needs the local SeqRepo/UTA/gene-norm services):
src/scripts/run-release.sh 2026-11-08 --full-procs --skip-parquet --dry-run   # stages 0-4 run for real; stage 5 printed
src/scripts/run-release.sh 2026-11-08 --start-step 5 --skip-parquet           # build + validate, then publish

Gate per release: deltas[] grows by one, its checkpoint_full.month = 2026-11, baseline_release = the previous release; weekly/00-latest_weekly = the newest. Run oracle-delta-reconstruction.sh on the first delta (0,0,0). Do step 9 in the same session as the bootstrap: until then v1/1.1/index.json still says current. Rollback, only within minutes and only if nobody can have used it: delete v1/1.2/ and regenerate the root index from a 1.1.0 checkout (generate-r2-index.sh --line v1/1.1/) — [OK]. Otherwise fix forward (1.2.1).

9. Freeze v1/1.1/ [OK: live R2, deletes ~42 GB]¶

src/scripts/r2-freeze-line.sh v1/1.1/                     # dry run: plan, MANIFEST.json, README.txt (local)
src/scripts/r2-freeze-line.sh v1/1.1/ --keep-parquet                # dry run
src/scripts/r2-freeze-line.sh v1/1.1/ --apply --keep-parquet        # D3: parquet/ stays until step 13

Deletes weekly/ (incl. 00-latest_weekly), and parquet/ only without --keep-parquet; writes MANIFEST.json + README.txt; regenerates v1/1.1/index.json (status: frozen, superseded_by: v1/1.2, schema 1.1.0) and the root index; purges the deleted paths on the CDN; then runs verify-frozen. Gate: PASS: v1/1.1/ frozen; curl the public v1/1.1/index.json and README.txt; a 1.1 monthly's sha256 is unchanged against MANIFEST.json. Rollback: the deleted weekly fulls and Parquet are not records and are not restored (any 1.1 week = a monthly + deltas); a wrong MANIFEST/README is rewritten by running the script again.

10. Official toolkit on the full, on GCP [OK: GCP spend, quote first ~$10–12]¶

Run the GA4GH gkm-toolkit validate_bundle_schema (strict, registry over schema/ at tag 1.2.0) on the published v1/1.2/clinvar-gkm_2026-11.json.gz on a VM, as for 1.1.0. Announce the quote, cap the spend, delete the VM after, and check nothing of ours is left running. Gate: 0 failures; record the result in release-validation.md.

11. Regenerate the examples [OK: PR merge into 1.0]¶

python src/scripts/extract-example.py --bundle <v1/1.2 2026-11 full> --all

Gate: pytest src/scripts/tests/test_extract_example.py; the 42 examples validate (rs + toolkit); the VCV/RCV examples show the #225 aggregate primaryCoding. Same PR: release-validation.md 1.2.0 results, working-in-python.md (tag 1.2.0, a 1.2.0 sample bundle and delta), the frozen-line note in docs as needed.

12. Forward-merge 1.0 → main [OK: PR merge into main]¶

git switch -c chore/forward-merge-1.2.0 origin/main && git merge --no-ff origin/1.0. Gate: git describe origin/main is not exactly 1.2.0 (main stays dev); docs build; tests.

13. Parquet (#217 + gkm-bundle-parquet 2.0.0), immediately after step 8¶

From step 8 the DuckDB console reads v1/1.2/parquet/, which is empty until this step (D3). Land #217 on 1.0 (it is based on release/1.2.0; merge only with the maintainer's OK); publish v1/1.2/parquet/ from the newest release; drop --skip-parquet from the weekly command; then run the freeze again without --keep-parquet (r2-freeze-line.sh v1/1.1/ dry run, then --apply) so v1/1.1/parquet/ is deleted. Gate: the DuckDB console's Release label shows the 1.2 build; parquet/manifest.json schema_version 1.2.0. Then send the completion notice (email + Discussion) if it was held for Parquet.
