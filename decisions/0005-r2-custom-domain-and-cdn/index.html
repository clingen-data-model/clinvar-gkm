0005 — R2 distribution domain, CDN caching, and fee protection¶

  • Status: Accepted
  • Date: 2026-10-13
  • Spec (if any): —

Context¶

Public distribution originally pointed consumers at the R2 development URL https://pub-f0ad0e0dac0345408dcc95bda20beb42.r2.dev. That endpoint is explicitly dev-only: Cloudflare rate-limits it (429s under load), throttles bandwidth, and supports no CDN caching, WAF, or rate-limiting rules. We needed a stable, production-grade hostname that consumers can hardcode long-term, with cache/abuse controls in front of the bucket.

Constraints that shaped the choice:

  • clinicalgenome.org is not usable as the host. Its authoritative DNS is on AWS Route 53, and ClinGen has no Cloudflare account. R2 custom domains must live in a Cloudflare zone. The supported ways to attach a Cloudflare-served hostname to an externally-hosted parent domain are all gated: full setup (move the whole org domain to Cloudflare — not our call), Partial/CNAME setup (Cloudflare Business plan), or Subdomain setup (Cloudflare Enterprise). None were viable.
  • A generic downloads.clinicalgenome.org / data.clinicalgenome.org would wrongly imply an org-wide ClinGen download hub; clinicalgenome.org hosts many independent data sources.
  • R2's defining property is $0 egress — so "download bandwidth" is never a cost. The only download-driven cost is Class B (read) operations, which are cheap and collapse to near-zero behind a CDN cache.

Decision¶

  1. Dedicated domain. Registered clinvar-gkm.org via Cloudflare Registrar (~$10/yr), which creates it as its own free Cloudflare zone — no dependency on ClinGen's Route 53 or any admin.
  2. Public host = data.clinvar-gkm.org, attached to the clinvar-gkm R2 bucket via R2 → Connect Domain (auto-creates a proxied record + TLS). data (not downloads) because consumers also range-read the Parquet in place (DuckDB/httpfs), which isn't a "download". The apex is left free for a future landing page.
  3. Scripts default to the custom host, env-overridable. All uploaders + the index generator set R2_PUBLIC_URL="${R2_PUBLIC_URL:-https://data.clinvar-gkm.org}". generate-r2-index.sh writes this as the base_url in index.json / the root manifest / feed.xml — the canonical consumer URL.
  4. Fee protection is CDN-side (Cache Rules + one rate-limit rule), plus an optional --purge path in the uploaders for the rare in-place overwrite.

The pub-…r2.dev dev URL still resolves (same bucket) and can be disabled in the dashboard once all consumers have migrated.

Consequences¶

Easy: a stable branded URL, free egress, near-zero op costs behind caching, full WAF/cache control. Harder / must-know for future administrators — the runbook below.

Reproducing the setup (if the domain/zone ever has to be rebuilt)¶

  1. Register / add the zone: clinvar-gkm.org via Cloudflare Registrar (or add any domain you own and point its nameservers at Cloudflare — full setup, free). Must be in the same Cloudflare account as the bucket.
  2. Connect the bucket: R2 → clinvar-gkm → Settings → Custom Domains → Connect Domain → data.clinvar-gkm.org. Cloudflare creates the proxied record + provisions TLS. Wait for Active.
  3. Verify it's proxied (Cache/WAF rules only act on proxied traffic): 
    dig +short data.clinvar-gkm.org      # → Cloudflare anycast IPs (104.x / 172.67.x), not an origin IP
curl -sI https://data.clinvar-gkm.org/v1/index.json | grep -iE 'server|cf-cache-status'
#   → "server: cloudflare" + a "cf-cache-status:" header  ⇒ traffic is proxied, rules apply
    If a rule editor warns "may not be proxying traffic for (http.host …)", this is the check to run — R2 custom domains are proxied by design, so once Active the warning is a false positive.

Cache Rules (zone clinvar-gkm.org → Caching → Cache Rules)¶

Object layout splits into write-once / immutable vs rewritten-every-release / mutable. Note "latest" appears both as a directory (/00-latest/) and inside a filename (clinvar-gkm_00-latest.json.gz), and there are two index files plus a feed — the mutable matcher must catch all of them:

  • Immutable (dated, never overwritten): /v1/deltas/<YYYY-MMDD>/…, /v1/datasets/clinvar-gkm_<YYYY-MM>.json.gz, /v1/datasets/parquet/<YYYY-MM>/…, /v1/archives/….
  • Mutable (rewritten every release): root /index.json, /v1/index.json, /v1/feed.xml, /v1/datasets/clinvar-gkm_00-latest.json.gz, and everything under any /00-latest/ tree (/v1/deltas/00-latest/…, /v1/datasets/parquet/00-latest/…).

Two rules; last matching rule wins, so keep the pointer rule below the immutable rule:

Rule 1 "R2 immutable artifacts"   (FIRST)
  When:  (http.host eq "data.clinvar-gkm.org")
  Then:  Eligible for cache; Edge TTL = Ignore cache-control, 1 month; Browser TTL = 1 day

Rule 2 "R2 mutable pointers"      (SECOND / last)
  When:  (http.host eq "data.clinvar-gkm.org") and (
           http.request.uri.path contains "00-latest"
           or http.request.uri.path contains "index.json"
           or http.request.uri.path contains "feed.xml" )
  Then:  Bypass cache

This collapses Class B cost (immutable files serve from edge, never hitting R2) while mutable pointers are always fetched fresh. The long TTL is safe only because dated artifacts are write-once — see overwrite gotcha below. Two Free-plan constraints shaped this:

  • Max cacheable object = 512 MB (Free/Pro/Business; Enterprise 5 GB). The multi-GB JSON bundles therefore never cache — they always report cf-cache-status: DYNAMIC and stream straight from R2. That is fine: egress is $0 and it's one cheap Class B op per fetch. Caching's real win is the smaller/hot files (Parquet sections, manifests, index).
  • Minimum dashboard Edge TTL = 2 hours on Free. You can't set a short TTL for the pointers that way, so Rule 2 uses Bypass cache (always fresh) instead of a 1-minute TTL. If brief pointer caching is ever wanted, stamp Cache-Control: max-age=60 on those objects at upload and set Rule 2 Edge TTL to "use cache-control header if present" (origin TTLs aren't subject to the 2 h floor).

Verify with real GET requests (curl -I/HEAD reports DYNAMIC even when a GET caches): 

u=https://data.clinvar-gkm.org/v1/deltas/<date>/manifest.json
curl -s -o /dev/null -D - "$u" | grep -i cf-cache-status   # run twice → MISS then HIT (immutable)
curl -s -o /dev/null -D - https://data.clinvar-gkm.org/v1/index.json | grep -i cf-cache-status  # DYNAMIC/BYPASS

Rate-limiting rule (Security → WAF → Rate limiting rules; 1 free IP-keyed rule)¶

When:  (http.host eq "data.clinvar-gkm.org")
Rate:  300 requests / 1 minute per client IP
Then:  Block for 10 minutes

Keep it generous (300, not tight): DuckDB/httpfs issues many range GETs per query, and cached hits still count toward the limiter. This is an anti-runaway backstop only — real exposure is pennies (free egress + $0.36 / million Class B).

Costs (order of magnitude)¶

Storage $0.015/GB-mo (a few $/mo at current size); Class B $0.36/million reads with 10M/mo free; egress $0. Caching + the write-once layout keep origin reads near-zero. There is no native hard spend cap — add Account → Notifications alerts on R2 storage/operations to catch a spike.

Overwrite gotcha + the --purge flag¶

Within the 1-month immutable Edge TTL, Cloudflare serves cached bytes without revalidating against R2, and the cache is per-PoP. So overwriting an already-cached immutable file in place (e.g. re-publishing a release under the same date, or re-running a backfill over an existing month) serves stale, inconsistent content for up to a month. Routine releases are safe — they write new dated keys, and the only paths they overwrite (index.json, 00-latest/*) are on the 1-minute rule and self-heal.

For the rare in-place overwrite, the uploaders take --purge, which purges the CDN cache for the dated path(s) just written:

  • upload-gkm-delta-to-r2.sh … --purge → purges …/v1/deltas/<YYYY-MMDD>/
  • upload-gkm-to-r2.sh … --purge → purges the dated monthly + dated Parquet set
  • backfill-monthly-to-r2.sh … --purge → purges ${DEST} (+ dated Parquet)

--purge requires a zone-scoped Cloudflare API token with Cache Purge permission (the object-scoped r2 token cannot purge), plus the zone id:

export CF_ZONE_ID=<clinvar-gkm.org zone id>
export CF_PURGE_TOKEN=<zone-scoped token with Cache Purge>
./upload-gkm-delta-to-r2.sh 2026-07-06 delta.json.gz manifest.json --purge

Without --purge nothing changes (routine behavior). With --purge but no token, the script warns and skips (non-fatal). Overridable host via CF_PUBLIC_HOST (default data.clinvar-gkm.org). All purge methods (URL, prefix, hostname, tag, everything) are available on all plans since 2025-04. Manual equivalent: 

curl -X POST "https://api.cloudflare.com/client/v4/zones/${CF_ZONE_ID}/purge_cache" \
  -H "Authorization: Bearer ${CF_PURGE_TOKEN}" -H "Content-Type: application/json" \
  --data '{"prefixes":["data.clinvar-gkm.org/v1/datasets/"]}'   # or {"purge_everything":true}

CORS¶

Bucket CORS is applied out-of-band (apply-r2-cors.sh with an admin token, or the dashboard; policy in src/scripts/r2-cors.json) and is returned at the bucket level, so it passes through the custom domain. The docs download browser (docs/assets/js/r2-browser.js) now fetches from data.clinvar-gkm.org; ensure the docs-site origin is allowed in r2-cors.json.

Optional future: a clinicalgenome.org entry point¶

If a ClinGen-branded link is ever wanted, the Route 53 admin can host an S3 static-website redirect + Route 53 alias at e.g. clinvar-gkm-data.clinicalgenome.org → https://data.clinvar-gkm.org. Purely additive; not required for anything to work.

Bucket layout note¶

Only the v1/ tree is live. The bucket root holds just the thin index.json manifest (ADR 0004) alongside v1/; the pre-v1/ root datasets/ and deltas/ trees plus root README.txt were deleted on 2026-10-13. All uploaders (including backfill-monthly-to-r2.sh) and the docs now reference v1/… paths.
